## 一、项目定位与总体架构

本仓库是一个**面向农夫山泉经销商的进销存 + 移动协同一体化系统**，采用单体仓库（monorepo）形态，包含三套独立应用，共享同一个 MySQL 数据库（`nongfu_inventory`）：

```
┌──────────────────────┐      REST /JWT       ┌──────────────────────────┐
│  frontend (Vue3 SPA)  │ ───────────────────▶ │                          │
│  管理后台 Web 端       │                      │      backend (Node.js    │
└──────────────────────┘                      │      + Express REST API) │
                                              │      :3000                │
┌──────────────────────┐    /mini REST +JWT   │                          │
│  mini-program (微信)   │ ───────────────────▶ │    controllers/routes/   │
│  配送/下单/报销/业绩    │                      │    services/utils/mw     │
└──────────────────────┘                      └───────────┬──────────────┘
                                                          │ mysql2 连接池
                                                          ▼
                                              ┌──────────────────────────┐
                                              │  MySQL  nongfu_inventory  │
                                              │  (init.sql + 迁移脚本)     │
                                              └──────────────────────────┘

辅助目录：
  database/   数据库初始化、迁移、备份脚本（.bat）
  商品档案/   原始商品主数据（xlsx）与商品图片（png），由导入脚本消费、静态托管
  docs/       设计规格与计划（注意：README 已严重过时，见第八节）
```

**核心结论**：系统已从 README 描述的"5 模块基础进销存"演进为包含**管理后台 + 完整 RBAC + 报表/押金/报销**的中型业务系统（微信小程序已于 2026-08-23 彻底删除，后续重新开发），但**文档与代码严重脱节**，且存在两张"设计但未接线"的结算表（见第八节）。

## 三、真实数据模型（实际 ≠ README）

### 实际生效表（约 15 张）
**基础业务（init.sql）**

9. `delivery_fee_settlement` 配送费结算表 —— **死表，从未被读写**
10. `financial_settlement` 资金结算对账表 —— **死表，从未被读写**

**迁移/扩展（小程序相关已删除）**
11. `users` 管理后台账号（bcrypt 密码、role：admin/user）
12. ~~`mini_accounts` 小程序账号~~ —— **已随小程序删除（2026-08-23）**，库表可保留但无读写代码
13. `salesmen` 业务员（commission_rate 提成比率）
14. `sms_codes` 短信验证码
15. `barrel_deposits` 水桶押金（collect 收取 / return 退回）
16. `reimbursements` 报销单（0 待审 / 2 通过 / 3 拒绝，支持附件）
17. `machine_stations` 机台站点（量贩机/零售机通用，用 `machine_type` 区分：1=量贩机 / 2=零售机；字段：站点名称 `station_name`、地址 `address`、负责人 `manager`、负责人电话 `manager_phone`；软删除 `status=0`）

### 核心实体关系（关键外键）
- `orders.station_id → sub_stations`（分销/返货订单）
- `orders.machine_station_id → machine_stations`（量贩机/零售机供货订单，type 4/6）
- `orders.worker_id → workers`（配送员工）
- `orders.created_by → workers`（创建人/业务员）
- `order_items.order_id → orders`（级联删除）；`order_items.product_id → products`（RESTRICT）
- `inventory.product_id → products`（CASCADE 更新）
- `purchase_records.product_id / supplier_id → products / suppliers`
- ~~`mini_accounts.target_id` 指向 workers / sub_stations / salesmen（按角色）~~ —— `mini_accounts` 表已随小程序删除（2026-08-23）

## 五、核心业务流程

1. **商品建档**：`products` 录入多价格与配送费；库存随首次入库自动建记录。
2. **入库**（`stockIn`，事务）：校验商品 → `inventory` 数量+ → 写 `purchase_records`。
3. **创建订单**（`createOrder`，事务 + `FOR UPDATE` 行锁）：
   - 解析蛇形/驼峰字段 → 生成 `SZX+YYYYMMDD+5位序号` 订单号；
   - 按订单类型计算单价与配送费 → 写 `orders` + `order_items`；
   - **逐条扣减 `inventory`（销售允许负数）**；
   - 若为**水站分销(type=2)**，累加 `sub_stations.current_debt`。
   - ⚠️ **不写入任何结算/对账表**（见第八节）。
4. **订单取消（canceled_at 口径）**：`orders` 表已移除 `order_status` 列（2026-08-23），订单取消改为设置 `canceled_at` 时间戳（非空即已取消），替代原 `order_status = 3`。
   - 取消时**回补库存**、若为水站订单**扣减欠款**（保留库存/欠款回滚与审计）；
   - 仪表盘与统计均以 `canceled_at IS NULL` 排除已取消订单；
   - 已移除"更新订单状态"接口（`PUT /:id/status`）与"仅待处理可改单"守卫（`updateOrder` 现允许修改任意未取消订单）。
5. ~~**小程序配送**~~ —— 小程序已删除（2026-08-23），该配送工作流（worker 接单/完成/上传照片、admin 指派）随之移除。
6. **押金/报销**：水桶押金收取/退回；报销单创建 → admin 审批（通过/拒绝 + 审批金额）。
7. **报表**：仪表盘汇总（库存总值、本月销售额=当月全部订单排除已取消、水站总欠款、待配送订单数=自有员工配送且未分配配送员）+ 7 天趋势（排除已取消）；商品销售统计按时间/类型/分类聚合（**2026-08-19 改版：仅统计数量、不含金额**）；**营收统计（2026-08-24 重建）**：按订单类型聚合营收——线上平台销售/线下水站返货=（进货价+总包配送费）×数量、线下水站分销=分销价×数量、线下零售=零售价×数量（下单手动填写，`createOrder` 快照手填值）、量贩机/零售机=机台售价×销量（销量来自 `machine_sales` 表手动录入，营收=售价×销量），均不含已取消订单。

## 七、代码组织规范与约定

- **分层缺失**：Controller + Route 一一对应；**DAO/Repository 不存在**，SQL 散落 Controller。（原 `scopeService` 随小程序删除已移除。）
- **命名**：DB 列为 snake_case；API 响应统一驼峰（`formatOrder` 等转换函数）；**请求体同时兼容 snake/camel**，导致 Controller 大量 `x !== undefined ? snake : camel` 兼容代码（冗长易错）。
- **统一响应包**：`{ code, message, data }`；分页 `{ list, total, page, pageSize }`（`utils/response.js`）。
- **事务约定**：库存/欠款/订单相关写操作均 `getConnection → beginTransaction → … FOR UPDATE → commit/rollback`，回滚在 catch、释放连接在 finally。
- **ID 生成**：订单号 `SZX+YYYYMMDD+5位`；进货单号 `PR+时间戳+4随机数`；配送/报销用自增。
- **错误处理**：`utils.error` 用 `res.status(code)`，但登录等失败用 `res.json` 返回 500（无 HTTP 状态码）；全局错误处理器直接回显 `err.message`（**信息泄漏风险**）。

## 八、技术债务与风险清单（进一步开发的重点注意事项）

> 优先级：**P0（阻断/安全风险）> P1（功能缺口/数据风险）> P2（维护性）**。

### P0 — 安全与数据风险
1. **JWT 密钥硬编码**：`nongfu_inventory_secret_2026` 在 `auth.js`/`authController.js` 两处重复且兜底值相同。必须移入 `.env`/密钥管理；当前任何拿到源码者均可伪造 token。
2. ~~**RBAC 数据隔离**~~：原 `scopeService` 与 `mini*Controller` 随小程序删除已移除；管理端当前无行级数据隔离，station/salesman 等角色若后续引入需重新设计。
3. **全局错误回显 `err.message`**：可能泄露 SQL/内部栈信息给前端。

### P1 — 功能性缺口 / 数据完整性
4. **结算与对账功能未实现（最关键的缺口）**：`delivery_fee_settlement` 与 `financial_settlement` 在 README 与表注释中被描述为"农夫山泉↔经销商↔水站↔员工"资金流转的核心，但**全代码无任何写入/读取**。订单创建不生成结算单。要么实现该链路，要么从 schema/文档中移除，避免误导。
5. **库存允许负数（超卖风险）**：`createOrder` 销售扣减库存注释明确"允许负数"，`stockOut` 仅盘库(type=3)放行负数。**正常销售不应让库存变负**，需明确负数策略或在下单时做库存校验。
6. **订单号并发竞争**：`generateOrderId` 用 `LIKE` 取当日最大序号 +1，无乐观锁/唯一约束保护，同一天高并发可能生成重复主键导致插入失败（仅被 catch 兜底为 500）。建议改用数据库序列或 `INSERT … ON DUPLICATE`/唯一约束 + 重试。
7. ~~**订单类型 5 语义标签不一致**：`statisticsController` 误标为"供货"，应统一为"返货"。~~ —— **已修复（2026-08-19）**。

### P2 — 架构与维护性

11. ~~小程序 `BASE_URL` 硬编码~~：小程序已删除（2026-08-23），该项不再适用。
