### 8/27 — 营收口径与成本模块重构
- **去除订单级配送费**：`orders.delivery_fee` 一律 0（新建/编辑），历史订单已清零；营收改用订单商品 `total_delivery_fee`（总包配送费，创建时快照）口径，`financialController` 不再读订单配送费。
- **营收（财务）页面卡片拆分**：官方平台销售 → 原货款(进货价)/总配送费/总计 3 卡；直营水站销售 → 返货价值(水票抵扣进货价)/总包配送费/分销价合计/总计 4 卡（接口返回 `goodsAmount/deliveryFee/ticketValue/revenue`）。
- **机台供货(type 4/6)订单不再计价**：单价/金额/应收均 0，价格在机台销量录入；财务 type 4/6 营收严格来自 `machine_sales`（为空=0）。
- **水票抵扣不计订单金额**（type 2 行级）：抵扣件数金额=0，未抵扣件数按分销价计入；表单中水票抵扣行单价/小计列显示 `-`；打印单价列显示「水票抵扣」。
- **菜单调整**：官方平台销售/机台供货订单不显示金额；「水站返货管理」更名为「水站账户管理」。
- **工资统计模块新增**：按订单计算配送员工资（type1/3=工人零售配送费、2=水站、4/6=机台 × 数量），按月统计（`/api/salary`，独立一级菜单后移入成本统计）。

### 8/28 — 成本统计子模块成型
- **成本统计（一级菜单 /cost）**重构为四个子项：**成本汇总 / 直营水站成本统计 / 其他支出 / 工资统计**（原固定支出、5 类营业成本页面已废弃）。
- **直营水站成本**（/cost/station，`/api/cost/station-summary|station-orders|order-items`）：type 2 水票抵扣商品成本 =（进货价 + 水站分销配送费 `distribution_delivery_fee`）× 抵扣件数，按水站汇总。
- **工资统计**（/salary，`/api/salary/summary|orders|order-items`）：员工配送费按订单类型费率快照 × 数量，按月/员工汇总 + 订单/商品明细下钻。

### 9/2 — 其他支出、成本汇总、公司账户管理、工资发放
- **其他支出**（/cost/expenses，`/api/expenses`）：手动录入支出（名称/金额>0/日期/类别[预置+自定义]/支出账户/备注），CRUD 全事务（选账户=扣 `finance_accounts` 余额 + 记 `finance_transactions` 支出流水；删除撤销回补）；导入 xlsx/csv（模板下载、逐行校验跳错）、导出 xlsx/csv、类别接口。
- **成本汇总**（/cost/summary）：月份 + 4 卡（直营水站成本/员工工资/其他支出/成本合计）+ 三明细 Tab（前端并行三接口组合）。
- **公司账户管理**（一级菜单下 基础信息管理 → 公司账户管理 /accounts，`/api/finance-accounts` 扩展）：`finance_accounts` 扩为 **7 类账户**——1 晟之溪公户 / 2 水公社公户 / 3 微信 / 4 其他（资金账户）+ **5 可上单信用余额 / 6 可上单折扣余额 / 7 自有费用余额**（2026-09-02 新增，**相互独立、无业务语义的普通账户**）；支持账户 CRUD（删除限余额 0 且无流水）、人工收支、**任意账户间互转**（事务双流水同批次）、流水查询。
- **工资发放**（工资统计页，`salary_payments` 表）：员工+月份唯一发放；确认发放弹窗（发放账户[全部启用账户]/发放月份[可改，实时刷新金额与状态]/发放金额只读快照/备注），确认=写发放记录 + 所选公司账户扣款 + 支出流水（`tx_category='工资发放'`，`related_module='salary_payment'`），已发放行金额锁定；支持撤销发放（回补余额+删流水+删记录）；汇总接口 LEFT JOIN 返回发放状态。
- **数据库全量包** `database/full_schema_data.sql`（30 表）为**一键部署（start.bat）唯一初始化源**，`init.sql`/各 migration 仅历史参考；新环境自动含 7 类账户与全部新表。

### 9/3 — 入库关联公司账户（扣款 + 流水 + 作废退回）
- **入库必选付款账户**：`purchase_records` 新增 `account_id / account_name / paid_amount / status / void_at / void_by / void_reason / handler`（迁移脚本 `database/migration_add_stockin_account.sql`，幂等）。

**入库扣款的适用边界（重要）**

| 入口 | 是否生成入库单 | 是否扣账户 |
|------|--------------|-----------|
| 入库弹窗（采购） | ✅ | ✅ 按合计扣款 |
| 盘库弹窗「库存增加」 | ✅ | ✅ 按 0 元扣款（需选账户，仅留痕） |
| 盘库弹窗「库存减少」 | ❌ 走出库 | ❌ |
| **Excel 导入库存** | ❌ 直接覆盖 `inventory.quantity` | ❌ |

Excel 导入定位为**库存数量校准/初始化**（盘点性质），不是采购行为、没有资金流出，因此不走入库单与扣款。若需对导入的库存补记采购成本，应改用入库弹窗录入。

**多商品提交的原子性说明**：入库弹窗一次提交多个商品时，前端按商品逐条调用 `POST /inventory/in`，每条是独立事务。前端提交前已用「账户余额 ≥ 全部商品合计」做总额预检，正常情况下不会中途失败；极端并发或单条数据异常时，已成功的条目会保留，前端提示"已完成 X 条后中断"并刷新列表，不会静默吞错。如需整单原子，需重构为「入库单头 + 明细」结构（当前未采纳）。

## 一、项目定位与总体架构

本仓库是一个**面向农夫山泉经销商的进销存 + 移动协同一体化系统**，采用单体仓库（monorepo）形态，包含三套独立应用，共享同一个 MySQL 数据库（`nongfu_inventory`）：

```
┌──────────────────────┐      REST /JWT       ┌──────────────────────────┐
│  frontend (Vue3 SPA)  │ ───────────────────▶ │                          │
│  管理后台 Web 端       │                      │      backend (Node.js    │
└──────────────────────┘                      │      + Express REST API) │
```

## 五、核心业务流程

1. **商品建档**：`products` 录入多价格与配送费；库存随首次入库自动建记录。
2. **入库**（`stockIn`，事务）：校验商品 → `inventory` 数量+ → 写 `purchase_records`。
3. **创建订单**（`createOrder`，事务 + `FOR UPDATE` 行锁）：
   - 解析蛇形/驼峰字段 → 生成 `SZX+YYYYMMDD+5位序号` 订单号；
   - 按订单类型计算单价与配送费 → 写 `orders` + `order_items`；
   - **逐条扣减 `inventory`（销售允许负数）**；
   - 若为**水站分销(type=2)**，累加 `sub_stations.current_debt`。
   - ⚠️ **不写入任何结算/对账表**（见第八节）。
4. **订单取消（canceled_at 口径）**：`orders` 表已移除 `order_status` 列（2026-08-23），订单取消改为设置 `canceled_at` 时间戳（非空即已取消），替代原 `order_status = 3`。
   - 取消时**回补库存**、若为水站订单**扣减欠款**（保留库存/欠款回滚与审计）；
   - 仪表盘与统计均以 `canceled_at IS NULL` 排除已取消订单；
   - 已移除"更新订单状态"接口（`PUT /:id/status`）与"仅待处理可改单"守卫（`updateOrder` 现允许修改任意未取消订单）。
5. ~~**小程序配送**~~ —— 小程序已删除（2026-08-23），该配送工作流（worker 接单/完成/上传照片、admin 指派）随之移除。
6. **押金/报销**：水桶押金收取/退回；报销单创建 → admin 审批（通过/拒绝 + 审批金额）。

## 七、代码组织规范与约定

- **分层缺失**：Controller + Route 一一对应；**DAO/Repository 不存在**，SQL 散落 Controller。（原 `scopeService` 随小程序删除已移除。）
- **命名**：DB 列为 snake_case；API 响应统一驼峰（`formatOrder` 等转换函数）；**请求体同时兼容 snake/camel**，导致 Controller 大量 `x !== undefined ? snake : camel` 兼容代码（冗长易错）。
- **统一响应包**：`{ code, message, data }`；分页 `{ list, total, page, pageSize }`（`utils/response.js`）。
- **事务约定**：库存/欠款/订单相关写操作均 `getConnection → beginTransaction → … FOR UPDATE → commit/rollback`，回滚在 catch、释放连接在 finally。
- **ID 生成**：订单号 `SZX+YYYYMMDD+5位`；进货单号 `PR+时间戳+4随机数`；配送/报销用自增。
- **错误处理**：`utils.error` 用 `res.status(code)`，但登录等失败用 `res.json` 返回 500（无 HTTP 状态码）；全局错误处理器直接回显 `err.message`（**信息泄漏风险**）。

## 八、技术债务与风险清单（进一步开发的重点注意事项）

> 优先级：**P0（阻断/安全风险）> P1（功能缺口/数据风险）> P2（维护性）**。

### P0 — 安全与数据风险
1. **JWT 密钥硬编码**：`nongfu_inventory_secret_2026` 在 `auth.js`/`authController.js` 两处重复且兜底值相同。必须移入 `.env`/密钥管理；当前任何拿到源码者均可伪造 token。
2. ~~**RBAC 数据隔离**~~：原 `scopeService` 与 `mini*Controller` 随小程序删除已移除；管理端当前无行级数据隔离，station/salesman 等角色若后续引入需重新设计。
3. **全局错误回显 `err.message`**：可能泄露 SQL/内部栈信息给前端。

### P1 — 功能性缺口 / 数据完整性
4. **结算与对账功能未实现（最关键的缺口）**：`delivery_fee_settlement` 与 `financial_settlement` 在 README 与表注释中被描述为"农夫山泉↔经销商↔水站↔员工"资金流转的核心，但**全代码无任何写入/读取**。订单创建不生成结算单。要么实现该链路，要么从 schema/文档中移除，避免误导。
5. **库存允许负数（超卖风险）**：`createOrder` 销售扣减库存注释明确"允许负数"，`stockOut` 仅盘库(type=3)放行负数。**正常销售不应让库存变负**，需明确负数策略或在下单时做库存校验。
6. **订单号并发竞争**：`generateOrderId` 用 `LIKE` 取当日最大序号 +1，无乐观锁/唯一约束保护，同一天高并发可能生成重复主键导致插入失败（仅被 catch 兜底为 500）。建议改用数据库序列或 `INSERT … ON DUPLICATE`/唯一约束 + 重试。
7. ~~**订单类型 5 语义标签不一致**：`statisticsController` 误标为"供货"，应统一为"返货"。~~ —— **已修复（2026-08-19）**。

### P2 — 架构与维护性
8. **缺乏数据访问层**：定价/结算逻辑在 `createOrder`/`updateOrder` 中**几乎完全复制**。建议抽离 `pricingService` + `settlementService` + `orderRepository`，消除重复、统一规则。

10. **静态资源路径硬编码**：`app.js` 用相对路径 `'../../商品档案/商品图片'`、`'../uploads'` 托管，依赖固定目录层级，迁移/部署易失效，应改为可配置绝对路径。
11. ~~小程序 `BASE_URL` 硬编码~~：小程序已删除（2026-08-23），该项不再适用。
12. **前端 Pinia 未落地**：已安装但无 store 模块，认证态/用户态散落 `localStorage` 与各组件，建议集中管理。
