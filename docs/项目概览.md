### 9/22（续 8）— 水票并发守卫（重复核销）+ 冒烟残留治理

**① 修一处资金侧并发缺陷（`writeOffTickets` 无并发守卫）**

- `SELECT` 待核销票是**普通读 + 无 status 复查的 UPDATE`：REPEATABLE-READ 下读到的是本事务首次读的快照，
看不到别人已提交的核销 → 同一批水票可被两笔订单各核销一次，后提交者覆盖 `order_id`，
  先提交的订单「已按抵扣价结算但没有任何票指向它」（账面看不出来）。
- 修法：守卫进 SQL —— `UPDATE … WHERE ticket_id IN (…) AND status = 未用`，并要求 `affectedRows === need`；
  ⚠️ 刻意不用 `SELECT … FOR UPDATE`（`water_tickets` 只有单列索引，锁定读会扩大间隙锁面）。
- 新增 `smoke_concurrency.js`（13 项，**无需后端**、服务层两连接、确定性、零残留）；
  修复前该冒烟第 1 段**红**、修复后全绿。同时给 `run_smokes.js` 增加「无需后端」分类。

**② 冒烟残留治理（一条链上的三个问题）**

- `smoke_mini_admin` 每轮泄漏 5 个**公司账户**：账户域走 API 创建，`account_id` 由**服务端生成**（`ACC…`），
  而清理与自检都按 `account_id LIKE 'SMKA%'` → **一条都匹配不到**；更要命的是**自检与清理用同一个错条件**，
  于是双双「通过」（实测积了 56 个）。已改为按**账户名**识别，并写进中央清理 `MARKERS.accounts`。
- 那批残留的同类型账户把 `smoke_order_revenue_posting` 的 `bal(type)`（无 ORDER BY、取 `r[0]`）顶偏 →
  出现**与业务无关的假失败**（生产入账是 `ORDER BY created_at LIMIT 1`，其实入对了）。已让断言与生产同序。
- `cleanup_smoke_data.js` **一直是坏的**：查 `mini_accounts.username`（该列已随小程序迁移移除）→
  整体报错回滚。同款问题在 `lib/smokeCleanup.js` 修过、这里漏改。已修，并补上冒烟公司账户的清理。
- 处置后只读体检：**全库零残留**、10 个真实账户余额无漂移、6 个水站欠款 0 偏差。

### 9/22（续 6）— Phase 7 落地（水票积分）+ 运维域「小程序账号管理」

#### 一、Phase 7：按「先收定价权、再动钱」分四步落地

① §12.6 单件值**落库**（`distribution_delivery_fee_unit`，不再靠「总额 ÷ 数量」反推）；
② §12.10 单件值**服务端重取**（一律取自商品档案，请求体值只作展示）；
③ §12.9 **停用**两个「直接改历史金额」的配送费调整端点（返回 410 + 前端入口移除）；
④ §12.7 发行**入账** / 作废·减量·删批次**回冲**（水站钱包；1 积分 = 1 元，下单可直接抵扣）。

金额逻辑抽成 `createIssuance` / `updateIssuanceCore`（Web 与管理端**共用一份**），
新增 `services/waterTicketLedger.js` 承载入账/回冲与「净入账」聚合。

被冒烟逐条钉死的**不变量**：

- 三列恒等：`unit × quantity === _total === 遗留列`；
- 方向固定：发行/加量 **IN**、作废/减量/删批次 **OUT**（原方向的反向）；
- **按净入账回冲**（不是按单据快照）：之前的票级作废与减量已冲回一部分，按快照会**多冲**；
- 回冲**允许被拒**（余额不足 → 整单 rollback，不制造负余额）；
- 账户调整补发的票**既不入账也不回冲**（不属于任何批次）。

⚠️ 顺带修一处真缺陷：钱包原语抛的是**业务错误**，而发行/编辑/删批次三处把它吞成 **500** ——
「积分不足所以不能作废」会表现为「服务器错误」。已统一按自带状态码回（400/404）。

#### 二、运维域「小程序账号管理」（不计入 17 个业务域）

禁用/启用、改绑定、解绑此前**只能改 SQL**（服务端的每请求校验早已生效，缺的只是管理入口）。
三条硬边界（不能操作自己 / 管理员账号不开放 / 改绑目标须启用且未被占用）**全部有反向断言**；
「**禁用**＝保留绑定（写 401、读可用）」与「**解绑**＝删绑定行（同一微信才能重绑）」
分别钉死 —— 用 `status=0` 冒充解绑会让用户永远登不进去。

### 9/22（续 5）— Phase 7 前置：水票写侧防线（当场抓出一处恒不生效的守卫）+ 营收区间静默退化修复

#### 一、先补防线，防线当场抓到真缺陷

Phase 7（水票积分）要改造 6 个发行类写端点，而它们此前**零冒烟覆盖**
（`smoke_ticket_restore.js` 只覆盖订单侧核销/还原）。按「改既有端点前先有防线」的纪律先定型现状，
新增 `backend/scripts/smoke_water_ticket.js`（**73 项**）。**它当场抓到一处真缺陷**：

`deleteIssuanceBatch` 的「批次内有已核销票则拒绝删除」守卫**参数顺序颠倒** ——
SQL 是 `IN (${placeholders}) AND status = ?`，参数却传 `[TICKET_STATUS.USED, ...ids]`，
绑定错位成 `issuance_id IN (2) AND status = 'WTI...'`，条件**恒不成立**（恒 0 行）。
后果：含已核销票的批次照样能整批删除，连带删掉订单已抵扣的水票记录 ——
**订单还在、抵扣记录没了，且账面看不出异常**。已修，并由冒烟第 6.1 条钉死。

#### 二、新增增量红线 R11：识别「守卫恒不生效」这一类

该缺陷不报错、不抛异常，只是永远放行 —— 比「门禁看见了却放行」更隐蔽一层。
新规则识别「`IN (${...})` 在前、其后还有 `?`，但参数数组首位不是展开」的形态，
并双向验证：错误顺序拦下、`SET status = ? WHERE ... IN (...)` 这类正确写法放行。
顺带给扫描器补了「下一行」上下文（SQL 与参数数组常分作两行，行内单规则覆盖不到）。

#### 三、营收区间静默退化（§7.4 登记项）已修

`financialController.resolveDateRange` 对未知 range 走 default 分支 → `today/today`，
接口照样返回 **200**，数值与 `range=day` 完全相同 —— 用错区间却看不出错。
改为未知 key 返回 `null` → 各出口回 **400**；顺带收紧 `custom`（缺一半日期同样 400，
不再静默忽略）。两侧断言同步（Web 与小程序各两条），§7.4 该项**已关闭**。

#### 四、Phase 7 剩余部分：处置方案已出具，待拍板

四项（积分入账/回冲 / 单件值与总额落库 / 停用两个「改历史金额」的调整端点 / 手机端开放发行）
已写成「现状 → 建议处置 → 回滚路径 → 待决」，见 `docs/小程序开发说明.md` §7.2。
⚠️ 顺序不可颠倒：**先把定价权收到服务端，再让数字进钱包** ——
否则就是「前端传多少、公司就欠水站多少积分」（违反设计文档 §22.1）。
待业务/财务确认「积分与人民币的会计口径」。

### 9/22（续 3）— 小程序 Phase 8b 第 16、17 域：回桶 + 系统设置（16/17）

#### 一、回桶（第 16 域）

- **8 接口 + 3 页**（押金台账 / 登记押金 / 桶型配置）。
- ⚠️ **服务层重构**：`barrelService` 的四个写操作改为「接收外部事务连接 + 抛 `bizFail`」。
  原约定（自管事务 + 返回 `{code,message}`）有两个问题：校验失败与成功走同一条返回路径、

  Web 控制器的事务边界随之上移；⚠️ 这是一次**签名变更**，直接调用服务层的
  `smoke_barrel.js` 随之同步（15/15 全绿，是本轮重构的守护）。
- ★ 断言重点：**方向**（收取=账户+ / 退回=账户−，抄反时台账照样对、只有余额错）
  与**跨端联动**（桶型停用后，登记表单不再列出、直接调接口也被拒）。
- ⚠️ 押金**没有改/删接口**：记错要开反向流水（同「入库单只能作废」）；
  有押金流水的桶型只能停用不能删（否则历史押金指向不存在的桶型）。

- ★ 跨端一致断言（Web 与小程序解析到同一位店长）；★ 手机号脱敏下发；

#### 三、⚠️ 本轮踩到的两个真问题（都已修并留痕）

1. **事务内读不到自己刚写的值**：`resolvePrintManager()` 固定用 pool 读，
   而小程序侧是在事务内写完后立刻读回 → 出现「设置成功但来源仍是回退」。
   修法：`getSetting` / `resolvePrintManager` 支持传入事务连接（read-your-writes）。
2. **改服务签名的连带影响**：`smoke_barrel.js` 直接调 `barrelService.deleteConfig(id)`，
   签名变更后报 `conn.query is not a function`。教训：改服务层签名必须**全局搜调用方**
   （grep 一次就能发现，比等冒烟报错快）。
   另：两处冒烟断言本身写错了（用 `/\d{7,}/` 判手机号，而测试数据自带 8 位时间戳数字 →
   误报；「回退到的人 ≠ 刚才那位」在库里只有一位店长时不成立）→ 改为「精确搜号码」与「与 SQL 口径比对」。

### 9/22（续 2）— 小程序 Phase 8b 第 12~14 域：营收 / 成本 / 利润（14/17）

#### 一、为什么三个域一次交付

三个都是**只读报表**，接口形状同构（区间 + 概览 + 按订单类型明细），没有幂等/审计/资金动作，
风险面只剩一条 —— **数字必须与 Web 端一致**。故 3 接口 + **1 个页面**（配置驱动三域切换）。

#### 二、取数单源（本批的技术核心）

把三个报表的**取数**从 Web 控制器里抽成可复用函数
（`loadFinanceSummary` / `loadCostOverview` / `loadProfitOverview`）并导出，
Web 端点改薄封装，小程序侧直接复用 —— **一行 SQL 都不写**。
对应的断言不是「接口 200」，而是 ★★ **跨端逐行一致**：同一区间下，
小程序与 Web 的总额、其他收入、以及 6 个订单类型的每一行都必须逐位相等
（只验 200 的话，两边各写一套 SQL 也能全绿）。另断言利润恒等式
`overall.profit === overall.revenue − overall.costTotal`。

#### 三、⚠️ 顺带挖出一个「静默错数据」陷阱（已登记待办）

`financialController.resolveDateRange` 的 switch 是 **`default` 兜底**：
未知 range（如 `quarter`）不报错，而是退化成「只算今天」。
冒烟已把它钉下来：`/api/finance/summary?range=quarter` 返回 200，

3. **编辑校验基于「合并后的值」而不是本次入参。**
   只提交 `salesmanMinPrice=99`（库中零售价 20）也必须被拒 —— 否则"先建一个合法组合、
   之后每次只改最低价"就能绕过上界检查。

#### 二、资金记账（与「其他支出」方向相反）

|                  | 其他支出        | 其他收入           |
| ---------------- | --------------- | ------------------ |
| 余额             | −amount         | **+amount**        |
| `tx_type`        | 2（支出）       | **1（收入）**      |
| `tx_category`    | 其他支出        | **其他收入**       |
| `related_module` | `other_expense` | **`other_income`** |
| 编辑/删除撤销    | 余额 +amount    | 余额 **−amount**   |

⚠️ 收入方向的撤销是**减** —— 照抄支出的 `+` 会变成「删一条收入反而再加一笔钱」，而余额恒等式仍可能「看起来」成立。已用「编辑后净变化 = 新值 − 旧值」「删除后回到基线」两条断言钉住。

#### 三、统计口径（**本节是口径的事实源**）

```
总营收 = 订单类营收(1/2/3/5) + 机台营收(4/6, machine_sales) + 其他收入(other_incomes)
总成本 = 订单商品成本(全类型) + 工资(在职应发) + 其他支出
总利润 = 总营收 − 总成本
```

- **取数单源**：新增 `backend/src/services/otherLedgerSummary.js`，把「其他支出 / 其他收入」两张台账的聚合收敛到一处（顺带把原先内联在 `dashboardController` 的 `loadOtherExpense` 下沉）。仪表盘 `metrics`/`trends`、`/finance/summary`、`/profit/overview` 四处统一从这里取数。
- **其他收入不进「按订单类型」的 6 行列表**：那是订单维度（1–6），塞入非订单类型会破坏维度语义（且 `smoke_cost_profit` 断言成本/利润 overview 恰好 6 行）。故它只进**总额**，并以独立字段 **`otherIncome`** 返回，由界面单独成行展示。
- **勾稽**：`sum(list.revenue) + overall.otherIncome === overall.totalRevenue`（有冒烟断言守住）。

#### 四、⚠️ 两个值得记住的坑

1. **本仓有两套区间约定，混用会静默漏掉当天数据**：
   - `utils/dateRange.buildRangeWhere` → start 含、**end 不含**（仪表盘 / 趋势 / 台账页）
   - `financialController.resolveDateRange` → start 含、**end 含**（营收汇总 / 利润汇总页）

   本次新增时即在营收汇总页踩到：`income_date < 今天` 把当天录入的收入全部排除，`otherIncome` **恒为 0**。修法是把约定**显式化为参数**（`loadLedgerTotal({ start, end, endInclusive })`）。

2. **「断言空转」会掩盖真 bug**：首轮冒烟 44/44 全绿，但恒等式那条打印的是 `0 + 0 vs 0` —— 数据全 0，等于没测，上面那个 bug 就是这么漏过去的。
   ⇒ **断言形式正确 ≠ 断言有效**；恒等式类断言必须同时断言「参与运算的量非 0」。

### 9/17（晚 7）— 修「量贩机 / 零售机 / 供应商无法删除」（并牵出两批真 bug）

**用户反馈**：量贩机、零售机、供应商信息无法删除。

**根因（三件事叠加，两件是真 bug）**：

1. **机台页「删除」按钮完全无反应（真 bug，且是"无法删除"的直接原因）**
   `MachineStationList.vue` 的 `handleDelete` 里写 `moduleTitle.value`，但脚本中只把 props 赋给了 `const props`（**模板能直接用 `moduleTitle`，脚本里不能**）→ 点击即抛 `ReferenceError`，**连确认框都不弹**。同类错误在 `@vue/compiler-sfc` 编译、`vite build`、token 门禁中**全都查不出来**。
2. **三处 `catch` 里误报成功（真 bug）**
   `SupplierList` / `StationList` 的删除、`WorkerList` 的保存，`catch` 分支里同样弹 `ElMessage.success('删除成功'/'新增成功')` → 请求失败也提示成功，用户以为删掉了。
3. **删除本质是软删（status=0），而列表默认不过滤状态** → 即使请求成功，该行仍在列表里，看起来"没删掉"。

**修复**：

- **删除语义统一为「无引用 → 物理删除；有引用 → 转停用」**（与员工删除同一套语义），响应 `{ mode: 'hard'|'soft', id, name, references }`；前端按 mode 给 `success`/`warning` 并展示引用清单。新增共用工具 `utils/deleteRefs.js`（`countRef` / `amountRef` / `describeReferences`）。
  - **机台**：引用 = 供货订单、销量记录。⚠️ `machine_sales.machine_id` 外键是 **ON DELETE CASCADE**，物理删机台会**连带删掉销量记录** → 有销量必须走停用。

### 9/17（晚 2）— 修「悬浮新建订单按钮点击无效」+ 新增真实浏览器 UI 冒烟

#### 一、Bug：悬浮按钮「拖得动、点不动」

**现象**：`components/FloatingCreateOrder.vue` 的悬浮按钮可以拖动，但**单击没有任何反应**（表单不弹）。

**根因（已由真实浏览器埋点实证）**：`onPointerDown` 里对**外层容器**调了 `setPointerCapture`。指针捕获后 `pointerup` 被重定向到捕获元素（容器）；而 `click` 事件的目标取「pointerdown 与 pointerup 目标的**最近公共祖先**」——因为按下时事件从 `<button>` 冒泡到容器才被处理，捕获元素是容器，于是：

```
pointerup → float-entry dragging   ｜   click → float-entry
```

`click` 落在容器 `.float-entry` 上，而处理函数 `@click` 挂在里面的 `<button class="float-btn">` 上 → **永远不触发**。拖动（走 pointermove/pointerup）不受影响，所以表现为「拖得动、点不动」。

**修复**：**激活改在 `pointerup` 里完成**——未拖动即视为点击，直接开表单；拖动结束则用一次性开关吞掉浏览器补发的 `click`（避免误开）。这样不再依赖会被重定向的 `click` 事件。`<button>` 上的 `@click` 仅保留给键盘（Enter/Space）路径，并有同一开关防重复触发。同时把 `setPointerCapture`/`releasePointerCapture` 显式指向 `wrapRef`（原先用 `e.currentTarget`，语义上依赖监听器挂载位置，易错）。

> 教训：**「拖得动但点不动」几乎总是指针捕获重定向导致 click 落点变化**。凡是用 pointer 事件实现拖拽的元素，激活逻辑不要依赖 `click`。

#### 二、新增：真实浏览器 UI 冒烟 `frontend/scripts/ui-smoke.mjs`

本次 bug 编译通过、构建通过、token 门禁通过——**三层静态检查全部漏过**，因为它只在「真实输入事件 + DOM 事件传播」层面暴露。故新增一层 UI 冒烟：

- **零依赖**：只用 Node 22 内置的 `WebSocket` + `fetch` 直连 **CDP**（Chrome DevTools Protocol），自动探测本机 Chrome/Edge（`--headless=new` 启动，独立临时 user-data-dir）。
- **真实输入**：通过 `Input.dispatchMouseEvent` 派发 `mousePressed/mouseMoved/mouseReleased`，Chromium 会据此合成真实 pointer 事件——这正是能复现本 bug 的关键（jsdom 之类的模拟 DOM 无法忠实还原指针捕获重定向）。

#### 一、员工删除：从「只软删」改为「能真删就真删，否则设离职」

**现象**：点删除后弹窗提示「删除成功」，但表格里那一行还在（只是状态悄悄变成「离职」），看起来删除无效。

**三个原因叠加**：

1. `DELETE /api/workers/:id` 只做**软删**（`UPDATE workers SET status=0`），而行本身仍在表中；
2. 员工列表默认**不限状态**（筛选默认「全部」），所以软删后该行照旧显示 —— 两者相加就是「提示成功但内容没动」；
3. **真 bug**：前端 `handleDelete` 的 `catch` 分支里也写了 `ElMessage.success('删除成功')`，请求失败时**照样报成功**（违反项目「失败分支不得误报成功」的约定）。

**改法（用户确认：能真删就真删，否则设离职）**：

- 后端 `deleteWorker` 先查引用表 `orders.created_by` / `orders.worker_id` / `financial_settlement.worker_id` / `salary_payments.worker_id` / `salary_advances.worker_id` / `staff_salaries.worker_id`：
  - 全为 0 → **物理 `DELETE`**，并清理 `system_settings` 中指向它的悬挂配置（物理删除后有引用的外键不会残留，因为本来就没有）；
  - 任一 > 0 → 软删 `status=0`，返回 `references: [{label, count}]` 与可读文案（如「存在历史单据（订单（配送员工） 1 条），已转为「离职」保留而非删除」）。
- 响应统一为 `{ mode: 'hard'|'soft', workerId, workerName, references }`；`DELETE` 走事务。
- 前端：`hard` 用 `success` 提示、`soft` 用 **`warning`** 提示（避免「提示成功却没少一行」的错觉）；`catch` 不再误报成功，并区分两类错误来源（HTTP 4xx/5xx 由页面提示、信封错误已由拦截器提示，不重复弹）。

### 9/11（晚 2） — 成本统计模块时间筛选：单月 → 预设区间 + 自定义

**背景**：成本统计四个页面（成本汇总 / 直营水站成本统计 / 工资统计 / 其他支出）此前筛选粒度不一：前三者只能选**单个自然月**，其他支出只能选日区间，且均无快捷预设。本次统一为「**本月 / 上月 / 本季度 / 今年 / 自定义**」按钮组，选「自定义」再露出日区间选择器。

**① 新增后端统一区间解析 `backend/src/utils/dateRange.js`**（三处控制器共用，避免各写一套日期数学）

- `resolveRange({ range, startDate, endDate, month })` → `{ start, end, startMonth, endMonth, isSingleMonth, range }`
- 约定 **`start` 含、`end` 不含**（`end` 为开区间终点），`buildRangeWhere(col, r)` 直接产出 `col >= ? [AND col < ?]` 与参数

**② 后端改动**

**③ 跨月区间的工资「已发放」口径**（本次唯一的语义变更）

`salary_payments` 按自然月存储，跨月区间无法对应单一发放快照。因此：

- 发放关联由 `salary_month = ?` 改为**区间月份聚合**：`salary_month BETWEEN startMonth AND endMonth`，`SUM(amount)` / `COUNT(*)` / `GROUP_CONCAT(salary_month)`，实现「**按发放月份落在区间内判定**」

**④ 前端新增 `components/DateRangeFilter.vue` + `utils/dateRange.js`**：预设只传 `range`（由后端解析区间，避免前后端各算一套），自定义传 `range + startDate/endDate`；点预设即查、自定义选完日期即查。四页接入；窄屏下按钮组换行、日期选择器独占整行；空态文案由「本月无…」改为「当前区间无…」。

### 9/14 — 修复商品图片上传 500（`PayloadTooLargeError`）

**现象**：商品管理新增/编辑时上传图片，接口返回 500（前端提示 `Request failed with status code 500`）。

**根因**：商品表单此前用 `FileReader.readAsDataURL()` 把图片转成 **base64**，塞进 `productForm.image`，随整个商品对象以 JSON 提交。而 `app.js` 的 `express.json()` 用默认限制 **100KB**，一张 205KB 的图片编码后必然超限 → body-parser 抛 `entity.too.large` → 500。另有两处放大该问题：`products.image_url` 是 `varchar(500)`，**存不下 base64**；系统既有 114 张图片走的是静态目录（`商品档案/商品图片/`，访问路径 `/product_images/xxx.png`），本就无需入库 base64。

**修复方式：改为文件上传落盘（与既有 114 张图一致）**

| 层       | 改动                                                                                                                                                                                                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 后端接口 | 新增 `POST /api/products/upload-image`（`productController.uploadProductImage` + `handleUploadImage`），multer 磁盘存储，落盘到 `商品档案/商品图片/`，**目录不存在自动创建**；返回 `{ path: '/product_images/<文件名>', url, filename, size }`                                                |
| 上传约束 | MIME 白名单 `png/jpeg/webp/gif/bmp`、单文件 ≤ 5MB、单次 1 个；文件名用 `generateId('IMG')` + 按 MIME 推导的扩展名（不信任用户端后缀）                                                                                                                                                         |
| 路由     | `routes/productRoutes.js` 注册为 `POST /upload-image`，**置于通配 `/:id` 之前**（否则被吞）                                                                                                                                                                                                   |
| 前端     | `ProductList.vue` 的 `el-upload` 由 `:auto-upload="false"` + `on-change` 改回 **http 直传**（`:action` 指向上传接口、`:headers` 带 Bearer token），成功回调取 `data.path` 写入 `productForm.image`；新增上传中禁用、格式/大小前置校验、失败提示；`api/product.js` 新增 `uploadProductImage()` |
| 图片预览 | 表单存**相对路径**，预览时统一拼后端 origin；`normalizeImageUrl()` 对历史「完整 URL / 重复前缀」数据做纠偏                                                                                                                                                                                    |

**顺带修掉的两个问题**

1. **失败分支误报成功（历史遗留坑）**：`handleSubmit` 与 `handleDelete` 的 `catch` 里原本调的是 `ElMessage.success` 并关闭弹窗，导致接口 500 时界面仍提示「新增成功 / 修改成功」。现改为如实 `ElMessage.error` 且提交失败**保留弹窗**便于重试。
2. **脏数据**：商品 `Pmrf3fgq30J6ZV3`（380mL天然水24入纸箱学习强国）的 `image_url` 为 `http://localhost:3000http://localhost:3000/product_images/SPBM003_image.png`（前缀重复两次），已修正为 `/product_images/SPBM003_image.png`；修复前已做全库备份（`database/backup_20260914_200755_before_image_fix.sql`）。

**不涉及表结构变更**——沿用既有 `image_url varchar(500)` 存相对路径，无需 migration。

## 五、核心业务流程

1. **商品建档**：`products` 录入多价格与配送费；库存随首次入库自动建记录。
2. **入库**（`stockIn`，事务）：校验商品 → `inventory` 数量+ → 写 `purchase_records`。
3. **创建订单**（`createOrder`，事务 + `FOR UPDATE` 行锁）：
   - 解析蛇形/驼峰字段 → 生成 `SZX+YYYYMMDD+5位序号` 订单号；
   - 按订单类型计算单价与配送费 → 写 `orders` + `order_items`；
   - **逐条扣减 `inventory`（销售允许负数）**；
   - 若为**水站分销(type=2)**，累加 `sub_stations.current_debt`。
   - ⚠️ **不写入任何结算/对账表**（见第八节）。
4. **订单取消（canceled_at 口径）**：`orders` 表已移除 `order_status` 列（2026-08-23），订单取消改为设置 `canceled_at` 时间戳（非空即已取消），替代原 `order_status = 3`。
   - 取消时**回补库存**、若为水站订单**扣减欠款**（保留库存/欠款回滚与审计）；
   - 仪表盘与统计均以 `canceled_at IS NULL` 排除已取消订单；
   - 已移除"更新订单状态"接口（`PUT /:id/status`）与"仅待处理可改单"守卫（`updateOrder` 现允许修改任意未取消订单）。

## 七、代码组织规范与约定

- **分层缺失**：Controller + Route 一一对应；**DAO/Repository 不存在**，SQL 散落 Controller。（原 `scopeService` 随小程序删除已移除。）
- **命名**：DB 列为 snake_case；API 响应统一驼峰（`formatOrder` 等转换函数）；**请求体同时兼容 snake/camel**，导致 Controller 大量 `x !== undefined ? snake : camel` 兼容代码（冗长易错）。
- **统一响应包**：`{ code, message, data }`；分页 `{ list, total, page, pageSize }`（`utils/response.js`）。
- **事务约定**：库存/欠款/订单相关写操作均 `getConnection → beginTransaction → … FOR UPDATE → commit/rollback`，回滚在 catch、释放连接在 finally。
- **ID 生成**：订单号 `SZX+YYYYMMDD+5位`；进货单号 `PR+时间戳+4随机数`；配送/报销用自增。
- **错误处理**：`utils.error` 用 `res.status(code)`，但登录等失败用 `res.json` 返回 500（无 HTTP 状态码）；全局错误处理器直接回显 `err.message`（**信息泄漏风险**）。
- **冒烟脚本收尾（2026-09-10 起强制）**：任何 `scripts/smoke_*.js` 凡写入数据，必须在 `finally` 中调用 `cleanupSmokeResidue(pool)`（`scripts/lib/smokeCleanup.js`），保证成功/异常路径都清理。测试数据命名必须带标记（员工/商品/客户名含「冒烟」，账号 `smoke_*`，商品编码 `SMK*`，日期用未来月份）以便被自动识别。**禁止**用 `products LIMIT 1` 之类的方式拿真实数据当测试对象。

## 八、技术债务与风险清单（进一步开发的重点注意事项）

> 优先级：**P0（阻断/安全风险）> P1（功能缺口/数据风险）> P2（维护性）**。

### P0 — 安全与数据风险

1. **JWT 密钥硬编码**：`nongfu_inventory_secret_2026` 在 `auth.js`/`authController.js` 两处重复且兜底值相同。必须移入 `.env`/密钥管理；当前任何拿到源码者均可伪造 token。
2. ~~**RBAC 数据隔离**~~：原 `scopeService` 与 `mini*Controller` 随小程序删除已移除；管理端当前无行级数据隔离，station/salesman 等角色若后续引入需重新设计。
3. **全局错误回显 `err.message`**：可能泄露 SQL/内部栈信息给前端。

### P1 — 功能性缺口 / 数据完整性

4. **结算与对账功能未实现（最关键的缺口）**：`delivery_fee_settlement` 与 `financial_settlement` 在 README 与表注释中被描述为"农夫山泉↔经销商↔水站↔员工"资金流转的核心，但**全代码无任何写入/读取**。订单创建不生成结算单。要么实现该链路，要么从 schema/文档中移除，避免误导。
5. **库存允许负数（超卖风险）**：`createOrder` 销售扣减库存注释明确"允许负数"，`stockOut` 仅盘库(type=3)放行负数。**正常销售不应让库存变负**，需明确负数策略或在下单时做库存校验。
6. **订单号并发竞争**：`generateOrderId` 用 `LIKE` 取当日最大序号 +1，无乐观锁/唯一约束保护，同一天高并发可能生成重复主键导致插入失败（仅被 catch 兜底为 500）。建议改用数据库序列或 `INSERT … ON DUPLICATE`/唯一约束 + 重试。
7. ~~**订单类型 5 语义标签不一致**：`statisticsController` 误标为"供货"，应统一为"返货"。~~ —— **已修复（2026-08-19）**。
