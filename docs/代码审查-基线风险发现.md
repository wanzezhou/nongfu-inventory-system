### 勘误一：#1 的前提不成立（成本汇总不会少算）

原描述：「`CostSummary.vue:169` 的 `pageSize: 500` 一旦超过 500 笔，**汇总数字会静默偏小**（资损面）」。

复核结论：**不成立**。该页的卡片金额与笔数取自后端 `getExpenses` 的 `sumAmount` 与 `total`——两者由**独立的 COUNT/SUM 全量聚合查询**得出（`expenseController.js:106-113`），与该次请求返回多少行明细无关。因此：

- 卡片金额**永远是全量的**，不会因 500 上限而少算；
- 页面导出走服务端导出接口，同样是全量；
- 真实问题只有两个：**① 明细表静默截断**（超过 500 笔时用户不知道只看到了一部分）；**② 「选项类」取数用分页上限**（这才是真会造成「少」的场景，见下一节）。

已按此修正处置：预览条数改为具名常量 `EXPENSE_PREVIEW_SIZE`，并在截断时**显式提示**「仅预览前 N 条（本区间共 M 笔），卡片金额与笔数为后端全量统计，完整明细请导出」——不做静默截断，但不改动汇总口径。

### 勘误三：#2 的实际暴露面比描述小

原描述强调 `/uploads` 下是 `delivery/`（配送照片）与 `reimburse/`（报销凭证），「配送照片通常包含客户门牌、签收现场」。复核后的事实：

- 全仓**没有任何代码写入** `backend/uploads/`（所有 multer 均为 `memoryStorage`；商品图写「商品档案/商品图片」）；
- 目录内实际只有 **1 个 0.1KB 的早期测试文件**，`reimburse/` 为空；
- 因此它当前是一条**无人使用的公开静态面**——定级 S1 偏高，实际更像「消除一条无主的攻击面」。

处置仍按最严做法执行（默认拒绝直连 + 收窄 CORP + UUID 文件名），但把这个事实记下来，避免后人误以为曾经泄露过真实凭证照片。

### 勘误四：门禁自身两处缺陷（已修）

1. **R1 从未抓到它要防的那个实例**。R1 的正则是 `/generateMockData|mockData|mockList|mockOrders|mockProducts|fakeData|FAKE_/`，而本仓唯一的假数据兜底叫 **`generateProductMockData`**（驼峰，中间夹了 `Product`）→ **不命中**。专门为历史缺陷 F2 写的规则，漏掉了 F2 的唯一现存实例。已补 `generate[A-Za-z]*Mock` 与 `Mock[A-Za-z]*Data`。
2. **R5 会误报全部正常分页**。原正则 `(pageSize|…)\s*[:=]\s*\d{2,}` 中的 `\d{2,}` 会匹配 `pageSize: 10`（两位），与它自己注释里写的「前端分页组件的默认值（10）不在此列」**自相矛盾**，使 23 处分页默认值全部成为误报。已把阈值改为 **3 位（≥100）**——真实的取数上限就是 100/200/500/999 这一档。

> 这两条本身也是「门禁腐化」的典型案例：**规则上线后必须用真实缺陷回归它一次**，否则会出现「规则在、缺陷也在」的假安全。

### #1 🔴 前端硬编码取数上限 → 成本汇总静默少算（资损面）

**位置**：`frontend/src/views/cost/CostSummary.vue:169`

```js
getExpenses({ ...q, page: 1, pageSize: 500 })
```

**问题**：成本汇总页拉取其他支出明细时硬编码上限 500 条。其他支出记录一旦超过 500 条，**汇总数字会静默偏小**——不报错、不提示，用户完全无感。这是资金口径错误，不是性能问题。

**同类扩散（已全量扫描，共 20 处，值域 {10, 100, 200, 500, 999}）**：

| 值 | 处数 | 高风险位置 |
|----|------|-----------|
| 999 | 2 | `statistics/ProductSales.vue:379,390` — 商品销售统计的选项数据全量拉取，超 999 静默丢数据 |
| 500 | 1 | `cost/CostSummary.vue:169` — **本项，资损面** |
| 200 | 3 | `waterTicket/WaterTicketManage.vue:504,505`、`finance/Finance.vue:552` |
| 100 | 8 | **`order/OrderFormDialog.vue:401,402,454,576,577`（5 处）**、`inventory/InventoryList.vue:293`、`waterTicket/WaterTicketManage.vue:499` |
| 10 | 6 | 各列表页默认值（此项合理，属正常分页） |

**值得单独指出**：历史缺陷 **F6** 正是"商品下拉只取前 100 条"，当时修复的是 `OrderList.vue`。而新建/编辑订单的核心表单 `OrderFormDialog.vue`（1016 行）里**至今仍有 5 处 `pageSize: 100`**。

> 这不是"漏了一个"，而是证明了**单点修复无法阻止同类复发**——同一个坑换了个文件又长出来了。这正是本轮要把这条写进 `eslint.config.mjs` 作为机器门禁的原因。

**建议**：
1. `CostSummary.vue` 改为服务端聚合接口返回汇总值（成本汇总本就应在 SQL 层算），前端不再拉明细自己加。
2. 建立"下拉/选项类数据"专用轻量接口（`id/name` 全量或远程搜索），参考 F6 对 `OrderList.vue` 的处置方式。
3. 所有分页接口在达到上限时**显式提示**（"仅显示前 N 条"），禁止静默截断。
4. 把"硬编码取数上限"落成 ESLint 规则（已写入 `eslint.config.mjs`，`Property[key.name='pageSize']` 字面量告警）。

### #2 🔴 `/uploads` 与 `/product_images` 在鉴权之外，且已放开跨域

**位置**：`backend/src/app.js:79`、`app.js:82`（静态资源） vs `app.js:91`（鉴权中间件）

```js
// 第 79、82 行——先挂静态资源
app.use('/product_images', express.static(path.join(__dirname, '../../商品档案/商品图片')));
app.use('/uploads', express.static(path.join(__dirname, '../uploads')));

// 第 91 行——鉴权只覆盖 /api
app.use('/api', apiLimiter, (req, res, next) => {
  if (AUTH_WHITELIST.has(req.path)) return next();
  return auth(req, res, next);
});
```

**问题**：全局鉴权中间件的作用范围是 `/api` 前缀，而 `/uploads` 与 `/product_images` 都是**根路径**，因此永远不会经过 `auth`。

`backend/uploads/` 下实际目录为 `delivery/`（配送照片）与 `reimburse/`（报销凭证）——配送照片通常包含**客户门牌、签收现场**，报销凭证包含**票据影像**。这些内容当前无需任何 token 即可访问（仅需知道文件名）。

同时 `app.js:37` 把 helmet 的 CORP 放开为 `cross-origin`：

```js
app.use(helmet({ crossOriginResourcePolicy: { policy: 'cross-origin' } }));
```

注释说明放开是为了让前端（5173）能加载商品图片。但该设置是**全局的**，副作用是任意第三方站点都可以直连嵌套这些资源——图片防盗链与隐私隔离同时失效。

`.gitignore` 已将 `backend/uploads/` 与 `商品档案/` 排除在版本控制外，说明团队明确视其为**运行期私密内容**，当前的可访问性与这个定位不一致。

**建议**：
1. 给 `/uploads` 挂鉴权：改为 `app.use('/api/uploads', auth, express.static(...))`，前端引用路径同步调整；或保留根路径但其前加 `auth` 中间件（注意前端 `<img src>` 无法带 Authorization 头，故更推荐后续引入**签名 URL / 短时 token 查询参数**方案）。
2. 商品图片属公开资产，可保留公开访问，但应把 CORP 放开**只作用于图片路径**，不要全局放开：

```js
// 商品图片单独放开 CORP，其余保持 helmet 默认（same-origin）
app.use('/product_images', helmet.crossOriginResourcePolicy({ policy: 'cross-origin' }),
        express.static(path.join(__dirname, '../../商品档案/商品图片')));
```
3. 文件名不可枚举化（UUID），避免"猜到文件名就能拿"。当前上传命名规则需一并确认。

### #14 🔴 历史风险 S7 从未闭环：65 处把 `err.message` 返回给客户端

**位置**：后端全目录，机器扫描命中 **65 处**，典型：

- `backend/src/controllers/dashboardController.js:72` — `return error(res, '获取统计数据失败: ' + err.message)`
- `backend/src/controllers/excelController.js:248` — `return error(res, '导出失败: ' + err.message)`
- `backend/src/controllers/excelController.js:515` — `return error(res, '导入失败: ' + err.message)`

**背景**：历史报告已识别此项（编号 **S7**，定级"🟡 中"），处置建议为"生产环境统一返回固定文案，`err.message` 只进日志"。但核对 `docs/技术债务审查报告.md` 第十节的 P0–P3 路线图（条目 1–17），**S7 从未被列入任何批次**，因此至今开放。

**为什么值得单独指出**：这不是"漏了一个 bug"，而是**风险登记与修复路线图脱节**——报告识别了、也写明了建议，但因为没有被排进批次，就永久停在"已识别"状态。这正是《代码审查流程.md》第六章"月度复发分析 + 门禁补强"要解决的问题：**识别不等于处置，登记必须带期限**。

`err.message` 在 MySQL 场景下会泄露表名、列名、SQL 片段、文件绝对路径（如 `ENOENT: no such file or directory, open 'D:\...\商品档案\...'`）、以及库名。

**建议**：
1. 新增统一错误出口：`error(res, msg, code)` 内部判断 `process.env.NODE_ENV === 'production'` 时输出固定文案，`err.message` 只写日志。
2. 分两步收敛：① 先改统一出口（一处生效，覆盖大部分场景）；② 再逐文件把拼接 `+ err.message` 去掉。
3. 本规则已落成机器门禁（`scripts/check-diff-hazards.mjs` 的 R4），**新增代码不会再引入**。

### #3 🟡 导出/导入接口沿用全局 10s 超时，与后端逐行写库模型冲突

**位置**：`frontend/src/api/request.js:8`（`timeout: 10000`）+ `frontend/src/api/excel.js`（三个接口均未覆盖 timeout）+ `backend/src/controllers/excelController.js`（导入为逐行 `execute`，循环内写入见 458/476/487 行）

**问题**：全局超时 10 秒，而 Excel 导入在后端是**事务内逐行 execute**。`multer` 上限 5MB，一个 5MB 的 xlsx 可达数千行，逐行写入远超 10 秒。

后果是**三态不可区分**：用户看到前端超时报错，但服务端可能 (a) 仍在执行、(b) 已提交、(c) 已回滚。用户会重试，而重试可能造成重复导入。

**建议**：
1. `api/excel.js` 的导入/导出接口单独设置 `timeout`（如导入 120s、导出 60s）。
2. 导入改为**批量多值 INSERT**（同时消除 N+1，见 #11）。
3. 前端区分"请求超时"与"服务端业务失败"两种提示；导入接口考虑改为**异步任务 + 轮询进度**。
4. 引入"导入幂等键"（如同一文件的批次 ID）防止超时重试导致重复导入。

### #4 🟡 `uncaughtException` 只记录不退出，进程带脏状态继续服务

**位置**：`backend/src/app.js:153-159`

```js
process.on('unhandledRejection', (err) => {
  console.error('未处理的Promise rejection:', err.message);
});
process.on('uncaughtException', (err) => {
  console.error('未捕获的异常:', err.message);
});
```

**问题**：Node 官方明确建议：`uncaughtException` 之后进程状态**不可信**，应记录后退出并由进程管理器（pm2 / systemd / nodemon）重启。当前实现会带着不确定状态继续处理请求——可能出现"一半事务已提交、连接已泄漏"的进程继续对外服务。

并且只打印 `err.message`，**丢失堆栈**，事后无法定位。

**建议**：记录完整错误（`console.error(err)`，含 stack）后 `process.exit(1)`；由 `start.bat`/进程管理器负责重启。`unhandledRejection` 同理（至少记录 stack）。

### #5 🟡 数据库不可用时服务照常启动，且无健康检查端点

**位置**：`backend/src/config/db.js:26-35`（`testConnection` 内部 try/catch 吞错）+ `backend/src/app.js:85`（调用未 await）

```js
// db.js：失败只打印，不抛出
} catch (error) {
  console.error('数据库连接失败:', error.message);
  ...
}

// app.js：不 await，不处理结果
testConnection();
```

**问题**：DB 未就绪时服务照常 `listen`，所有请求返回 500。运维侧无法区分"服务没起来"与"服务起来了但数据库不通"。

**建议**：
1. `testConnection` 失败时 `throw`（或返回布尔并由 app.js 判断后 `process.exit(1)`）。
2. 新增 `GET /health` 端点：返回进程状态 + 数据库连通性 + 连接池指标（`pool.pool._allConnections` 等）。这个端点应放在鉴权白名单内，便于监控探活。
3. 引入**优雅关闭**：`SIGTERM` 时停止接收新请求、`pool.end()`、等待进行中的事务结束。

### #6 🟡 连接池 10 连接 + 无界排队，长事务与高并发路径共用

**位置**：`backend/src/config/db.js:12-13`

```js
connectionLimit: 10,
queueLimit: 0,          // 0 = 无界排队
```

**问题**：`queueLimit: 0` 意味着请求可以无限排队——超时时间由客户端（前端 10s）决定，服务端无法主动保护自己。

风险叠加场景：Excel 导入持有连接执行长事务 + 工资批量发放 + 并发出库（每次都要 `FOR UPDATE` 行锁），三者叠加时会耗尽 10 个连接，后续所有请求排队。**排队期间前端 10s 超时**，用户重试进一步加剧排队。

同时缺失：`connectTimeout`、`idleTimeout`、慢查询观测。

**建议**：
1. 设置 `queueLimit`（如 50）与 `connectTimeout`（如 10s），超出时快速失败并返回 503 而非无限等待。
2. 长耗时任务（Excel 导入、报表导出）**不得占用业务连接池**——改用独立 pool 或异步任务化。
3. 事务内尽早 `commit`，禁止在事务里做非数据库操作（如文件 I/O、外部请求）。
4. 增加慢查询日志（`pool.on('acquire')` 计时或直接开 MySQL `slow_query_log`）。

### #7 🟡 鉴权失败返回 HTTP 200，与 `requireAdmin` 口径不一致

**位置**：`backend/src/middleware/auth.js:14`、`auth.js:22` vs `auth.js:32`

```js
// auth：HTTP 200 + body.code 401
if (!token) {
  return res.json({ code: 401, message: '未登录，请先登录', data: null });
}
...
return res.json({ code: 401, message: '登录已过期，请重新登录', data: null });

// requireAdmin（同一个文件）：403 用 HTTP 状态码
if (req.user.role !== 'admin') {
  return res.status(403).json({ code: 403, ... });
}
```

**问题**：同一个中间件文件里，401 走"业务码"、403 走"HTTP 码"，两种口径并存。

影响：
- Nginx 访问日志 / APM / CDN / 安全监控**无法从状态码识别未授权访问**，暴力破解与越权尝试在监控上不可见（`apiLimiter` 的 429 是有限流的，但 401 完全不可观测）。
- 前端 `request.js:33-40` 只能靠 `body.code` 判断；任何绕过 axios 的调用路径（blob 下载、`<img>`、直连）会漏掉 401 处理，表现为"页面白屏/无反应"而非跳登录。

**建议**：统一为 **HTTP 状态码 + body 双写**（`res.status(401).json({code:401,...})`），`requireAdmin` 已经这么做了，把 `auth` 对齐即可。若因历史原因必须保留 200，则需在《标准》中显式记录该约定，并确保所有非 axios 调用路径都被覆盖——但**不推荐**，代价大于收益。

### #8 🟡 无可观测性：无请求日志、无 traceId、无操作审计

**位置**：全仓——`app.js` 中间件链中无日志中间件；无 `requestId` 生成；无操作日志表（仅有 `created_by` 字段）

**问题**：这是资金与库存强审计场景，但当前无法回答：
- 谁在什么时候改了这笔账？（`created_by` 只记录创建者，不记录后续修改者）
- 某次线上 500 是什么请求触发的？（无请求日志）
- 一次前端报错对应服务端哪条日志？（无 traceId 串联）

**建议**：
1. 引入请求日志中间件（`pino-http` 或轻量自研），记录 `method / path / status / duration / userId / ip`。
2. 生成 `requestId`（`crypto.randomUUID()`），响应头回写，前端报错时上报——这是排查效率提升最大的一步。
3. 关键写操作（余额、库存、水票、订单）落**操作审计表**（who / when / what / before / after / requestId）。
4. 日志分级，`console.log` 不得进入业务代码（已落成 ESLint 规则）。

## 三、S3 建议

### #9 🟡 前端失败路径无统一策略

**数据**：前端 74 处 `catch` 块内容仅为 `console.error`，另有 **6 处完全空捕获**，形态完全一致（机器扫描 R2 命中 6 处）：

| 文件 | 行 |
|------|----|
| `frontend/src/views/order/OrderList.vue` | 192 |
| `frontend/src/views/inventory/InventoryList.vue` | 202 |
| `frontend/src/views/product/ProductList.vue` | 341 |
| `frontend/src/views/station/StationList.vue` | 204 |
| `frontend/src/views/supplier/SupplierList.vue` | 220 |
| `frontend/src/views/worker/WorkerList.vue` | 278 |

```js
// 六处均为同一形态（导出失败时的空捕获）
try {
  const response = await exportData('orders')
  downloadBlob(response.data, `订单数据_${Date.now()}.xlsx`)
} catch { } finally {
  exporting.value = false
}
```

**公平起见需要说明**：这是**当前尚可接受、但结构上脆弱**的写法，定级 S3 而非 S1。原因是 `request.js:45-53` 的响应拦截器对 `responseType === 'blob'` 的错误分支会解析 Blob 并弹出 `ElMessage.error('导出失败')`——所以用户**目前**能收到提示。空 catch 没有额外掩盖失败。

但它脆弱在两点：
1. 提示来自**拦截器的隐式副作用**，而非调用方的显式意图。一旦拦截器的 blob 分支被改动（例如为支持新的下载类型而调整），这 6 处会**同时**变成真正的静默失败，而且没有任何测试会发现。
2. 失败时 `downloadBlob` 不会执行，但没有"未生成文件"的显式反馈闭环。

**建议**：
1. 增加 Vue 全局错误处理（`app.config.errorHandler` + `onErrorCaptured`），统一上报与提示（配合 #8 的 requestId）。
2. 6 处空 catch 改为显式处理：`catch (e) { /* 错误提示由 request 拦截器统一给出 */ }` —— 至少写明依赖关系，让后续改动者知道不能随便动拦截器。
3. 空 catch 已落成机器门禁（ESLint `no-empty` + `check-diff-hazards.mjs` 的 R2），新增代码不会再引入。

### #10 🟡 `SELECT *` 仍有残留：机器扫描 43 处

**位置**：后端全目录，机器扫描 R3 命中 **43 处**，典型如 `backend/src/controllers/excelController.js:234`（`SELECT * FROM ${config.table}`），`orderController.js` 多处。

历史报告统计为 37 处，本次为 **43 处**——说明期间有新增。这本身是一个值得注意的信号：**存量债务在"清零"之后又长回来了**，与 #13 的机制缺失互为印证。

表名来自服务端白名单 `MODULE_CONFIG`，**无注入风险**（这一点做得对），但 `SELECT *` 会拖网络与内存，并在列变更时产生隐式耦合。

**建议**：通用导出改为使用 `config.columns` 中已声明的 `db` 字段列表拼列名（白名单内，安全），一举消除此处 `SELECT *`。本规则已落成机器门禁（R3）。
