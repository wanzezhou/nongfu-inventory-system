## 三、如何运行

### 3.1 启动后端（必须先启）

```bash
cd backend
node src/app.js
# 服务在 http://localhost:3000；探活用 GET /health（免鉴权、固定 200）
```

`backend/.env` 需要以下新增项（已写入本机 `.env`，`.env.example` 也已登记）：

```ini
JWT_SECRET_MINI=<64 位十六进制随机串>   # ⚠️ 必须与 JWT_SECRET 不同；缺失则后端拒绝启动
MINI_TOKEN_TTL=2h                      # 小程序令牌有效期
WX_APPID=                              # 微信登录用；留空则只能用本地开发登录
WX_SECRET=
MINI_DEV_LOGIN=1                       # ⚠️ 仅本地开发；生产必须删除或置 0
```

### 3.2 启动小程序

1. 微信开发者工具 → 导入项目 → 目录选择仓库下的 `miniprogram/`。
2. **AppID**：资质未就绪时可先用「测试号 / 无 AppID」（`project.config.json` 里是 `touristappid`）。
3. **详情 → 本地设置**：勾选「不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书」
   （因为 `config/index.js` 的 `API_ORIGIN` 是 `http://localhost:3000`）。
4. 编译后进入登录页。

### 3.3 首次登录怎么走

| 场景                            | 走法                                                                  |
| ------------------------------- | --------------------------------------------------------------------- |
| 已配置 `WX_APPID` / `WX_SECRET` | 点「微信一键登录」→ 未绑定时按提示授权手机号 → 服务端按手机号匹配身份 |
| 未配置微信凭据（当前默认）      | 登录页会提示，并可在「本地开发登录」里输入后台维护的手机号登录        |

**本地开发登录说明**（`POST /api/mini/auth/dev-login`，需 `MINI_DEV_LOGIN=1`）：

- 仍然要求手机号能匹配到**真实存在**的业务员 / 直营水站 / 管理员 —— 不创建任何假数据；
- 不允许自由选角色：`role` 只用于在**已匹配到的多条真实记录**里消歧
  （现状库中 `users.phone` 与 `sub_stations.phone` 确有重号，属真实数据特征）；
- 生产环境必须关闭。

## 四、接口契约

统一约定（后端既有规范，小程序侧严格对齐）：

- 前缀 `/api/mini`；响应信封 `{ code, message, data }`，HTTP 状态码与 `code` **双写**。
- **鉴权失败 = HTTP 401 + code 401**（小程序请求层在 `fail`/error 分支处理，不只看 `response.data.code`）。
- 无权限 = HTTP 403。
- 请求体**一律驼峰**（后端全局 `normalizeBody` 做蛇形→驼峰并删原键）。
- 令牌滑动续期：令牌过半生命周期时，响应头 `X-Mini-Token` 下发新令牌。

### 4.1 认证（§21.1）

| 方法 | 路径              | 鉴权             | 说明                                                                                                                              |
| ---- | ----------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| GET  | `/config`         | 公开             | 公开配置：`devLoginEnabled` / `wxLoginConfigured` / `tokenTtl` / `messages`（**不再含 `pickupConfigured`**）                      |
| POST | `/auth/login`     | 公开             | `{ code, phoneCode?, nickname?, avatarUrl? }` → `{ status:'OK', token, account }` 或 `{ status:'NEED_BIND', bindTicket, reason }` |
| POST | `/auth/bind`      | 公开             | `{ bindTicket, phoneCode }` → `{ token, account }`                                                                                |
| POST | `/auth/dev-login` | 公开（env 门禁） | `{ phone, role? }` → `{ token, account, devLogin:true }`                                                                          |
| POST | `/auth/logout`    | miniAuth         | 记审计；令牌无状态，实际登出由前端清 token                                                                                        |
| GET  | `/me`             | miniAuth         | `{ account, subject, wallet, blocked, role, permissions }`（**不再含 `pickup`**）                                                 |

### 4.2 商城（§21.2）

| 方法 | 路径                   | 说明                                                      |
| ---- | ---------------------- | --------------------------------------------------------- |
| GET  | `/products`            | `?keyword&category&page&pageSize`（pageSize 上限 50）     |
| GET  | `/products/categories` | 全量分类（**专用全量接口**，不走分页）                    |
| GET  | `/products/:id`        | 详情；水站额外返回 `availableTicketQty`、`stationDefault` |

按角色裁剪价格：业务员得 `retailPrice` + `salesmanMinPrice`（**不下发分销价**）；
水站得 `wholesalePrice`；管理员得全量。

### 4.3 订单（§21.4）

| 方法 | 路径                 | 说明                                          |
| ---- | -------------------- | --------------------------------------------- |
| POST | `/orders`            | 下单（**必须带 `clientRequestId`**，见 §6.2） |
| GET  | `/orders`            | `?status&page&pageSize`；主体条件来自令牌     |
| GET  | `/orders/:id`        | §32 的 16 项 + `minPriceCheck`                |
| POST | `/orders/:id/cancel` | 取消（**同时全额退款到钱包**，见 §6.4）       |
| POST | `/orders/:id/refund` | 退款（已发货/已完成路径）                     |

`POST /orders` 请求体：

```jsonc

  "clientRequestId": "SALESMAN:SM0011758...a1b2c3", // 幂等键，≤64，客户端生成
  "fulfillmentType": "DELIVERY", // ⚠️ 白名单，只接受 DELIVERY（自提已下线）
  "orderScene": "CUSTOMER_ORDER", // 仅业务员：SELF_PURCHASE | CUSTOMER_ORDER
  "customerName": "张三",
  "customerPhone": "13911112222",
  "customerAddress": "南京市…", // **必填**（自提下线后无免地址场景）
  "addressSource": "STATION_DEFAULT", // 仅水站：STATION_DEFAULT | ORDER_CUSTOM
  "remark": "下午送",
  "items": [
    {
      "productId": "Pmrf…",
      "quantity": 5,
      "unitPrice": 20, // 仅业务员可传；水站传了也会被服务端忽略（§9.1）
      "useTicket": true,
      "ticketQty": 3
    } // 仅水站
  ]
}
```

#### Phase 8b 管理员写操作 · 工资（第 11/17 域）

> ⚠️ **唯一「公司 → 个人」的资金动作**，也是最容易「静默错账」的一个。四条纪律：
> ① 实发 = 应发（可手动改，用于补加其他工资）− 待扣预支；**按实发扣账户**，不是应发；
> ② 实发为负（预支超过应发）= 挂账下月继续扣 → **不动账户、不写流水**；
> ③ 撤销发放是账户 **+** 回补（支出方向的撤销是加，抄成减会「撤一次反而再扣一笔」）；
> ④ 预支登记**即扣款**、发放时才抵扣 —— 两件事分开，别混成一个动作。
>
> ⚠️ **预支没有「同员工同月唯一」约束**（发放有）→ 它才是幂等键最该保护的地方：
> 弱网重试一次就是真的再预支一笔、账户再扣一次，两笔都合法、账面看不出来。
>
> **有意不做**：① 不提供「编辑发放金额」（发放单要么撤销重发、要么不动 ——
> 直接改金额会让它与 `finance_transactions` 的快照对不上）；
> ② 不提供「批量发放全员」（手机上一键给全员发钱，错一次就是几十个人的账要逐个撤）。
>
> ⚠️ **个人信息**：汇总列表**不下发 `phone`** —— `services/salarySummary.loadSalarySummary`
> 会带出手机号（Web 统计页要用），小程序端逐字段显式映射把它挡掉（见 §八）。

> **两件事**：押金台账（收/退押金，**资金动作**）与桶型配置（押金单价）。

> ⚠️ **方向**：收取押金 = 账户 **+**，退回 = 账户 **−**。方向抄反时台账照样能对上
> （两类流水都在 `barrel_deposit` 下），只有余额会错 —— 故冒烟把方向写在断言名里。
>
> ⚠️ **没有「编辑/删除押金」接口**：押金是一笔已发生的收付，记错要开一笔反向流水
> （退回/再收），不能改历史 —— 与「入库单只能作废」同一原则。
> （原生 SQL 直删押金会绕过账户回冲，与订单删单是同一类陷阱。）
>
> ⚠️ **桶型配置是跨端联动的配置**：停用/删除后，押金登记必须被拒 ——
> 冒烟对此有专门断言（只验「配置改对了」等于没验，定式 ⑫）。
> 有押金流水的桶型**只能停用不能删**（删了会让历史押金指向不存在的桶型 = 数据悬挂）。
>
> ⚠️ **服务层重构**：`barrelService` 的四个写操作改为「接收外部事务连接 + 抛 `bizFail`」
> （原为自管事务 + 返回 `{code,message}`）。原约定下校验失败与成功走同一条返回路径、
> 且事务边界散在服务层，调用方无法把幂等与审计并进同一事务（定式 ⑥）。
> Web 控制器的事务边界随之上移到控制器；既有守护冒烟 `smoke_barrel.js`（15 项）已同步并全绿。
>
> ⚠️ **个人信息**：押金台账（流水与汇总）**不下发明文手机号** ——
> 服务层的 `partyName` 对零售客户会拼成「姓名（电话）」，小程序侧逐字段重建名称。

### 5.1 自提已下线（2026-09-20 业务决定），原 `delivery_type = 3` 决策随之作废

**背景**：文档 §10.1.1 要求把「自提订单的 `delivery_type` 取什么值」在实现时定死，
本交付第一版据此决策为 **自提 → `3`（无需配送）**，并登记为待评审项。

**变更**：业务方决定**取消自提**，且要求**前后端一并移除**（不是只隐藏入口）。
因此上述决策不再是「已定死的取值」，而是**随功能一并作废** —— 该常量
（`constants/mini.js` 的 `PICKUP_DELIVERY_TYPE`）已删除。

移除范围与现存口径：

| 项              | 现状                                                                                           |
| --------------- | ---------------------------------------------------------------------------------------------- |
| 履约方式        | **只接受 `DELIVERY`**，白名单校验（非黑名单，变体拼写同样被拒）；缺失不默认放行                |
| 配送地址        | **每单必填**（原先「自提可免地址」的分支已删）                                                 |
| `delivery_type` | 只可能为 `1`（业务员/自有员工配送）或 `2`（水站配送）—— 不再产出「无需配送」的订单             |

| 前端            | 无任何自提入口/字样/禁用的灰按钮；订单列表「待自提」页签、首页「待自提」统计与待办均已移除     |
| 接口契约        | `/config` 去掉 `pickupConfigured`、`/me` 去掉 `pickup`（契约冒烟**反向断言**它们不再出现）     |

### 5.2 `wallet_transactions` 比文档多一个 `direction` 列

文档 §11.7 第 5 条记录了一个真实事故：**收入类流水的撤销是 `−amount`，抄成 `+` 会变成
「撤一次反而再加一笔」，而恒等式看起来仍然成立**。该坑的成因正是「用流水类型反推方向」。

因此本实现把方向**显式落库**：`amount` 恒为正数，方向只看 `direction`（1 入 / 2 出）；
撤销时取「**原方向的反向**」而不是按新类型再推一次。`reverseTransaction()` 的入参
刻意不接收 `direction`，从接口形状上堵住写反的可能。

### 5.3 取消与退款的优先级（文档 §16.1 要求实现时定死并回写本节）

| 路径     | 允许的履约状态                    | 结果                                                                                     |
| -------- | --------------------------------- | ---------------------------------------------------------------------------------------- |
| **取消** | `PAID` / `PROCESSING`（尚未发货） | 钱包全额退款 + `refund_status=REFUNDED` + `canceled_at` + 履约=`CANCELED`                |
| **退款** | `DELIVERING` / `COMPLETED`        | 钱包全额退款 + `refund_status=REFUNDED`，**履约状态保留退款前最后事实**（§16.1 第 3 条） |

> ⚠️ 2026-09-20 自提下线：退款允许状态中的 `READY_FOR_PICKUP` 已移除（该状态已退役）。

**为什么取消必然同时退款**：小程序订单是**下单即钱包支付**（§14.1），不存在「未支付的取消」，
所以取消与退款在小程序侧天然重合；Web 侧未支付订单的取消仍只走 `canceled_at`。

**库存 / 水票恢复条件**（§15.3「恢复库存（符合条件时）」的落地）：
当且仅当 `fulfillment_status !== COMPLETED` 时恢复。
已完成交付后退款属「已出货」，需实物退回后人工盘库，不能自动加回。

> ⚠️ 实现上**刻意不复用** `orderPricingService.restoreSalesEffects`：它内含「扣减水站
> `current_debt`」，而小程序水站订单从未增加欠款（§6.5.1），复用会让欠款变成负数。
> 库存恢复改用 `deductInventoryForSale(conn, productId, -qty)` —— 同样走行锁与存在性校验。

### 5.4 业务员成交价：前端可填 + 服务端强制下界（两处不是重复）

| 位置                                                   | 作用                                                         | 性质         |
| ------------------------------------------------------ | ------------------------------------------------------------ | ------------ |
| 前端 `order-confirm`（**成交价输入框**，`type=digit`） | 初值 = 参考零售价，可改；低于最低价时禁用提交按钮 + 红字说明 | **体验优化** |
| 服务端 `orderPricingService.assertSalesmanMinPrice`    | 事务内强制校验，不通过抛 bizFail → 400                       | **安全边界** |

**为什么前端必须有这个输入框**：Phase 3 明确要求「成交价（前端可填）」，确认订单页字段清单也含「成交价」。
缺少输入框时，最低价校验将退化为「拿档案零售价与下界比大小」——规则还在跑，但**保护对象没了**。
本期已补齐：默认值取 `retail_price`（§8.6 历史成交价「只作参考，不自动覆盖当前成交价」，
故不预填历史价），下界提示取 `salesman_min_price`。

前端改价后**立即重算**行小计、合计预览与红字校验，计算收敛在 `computePricing()` 一个纯函数里
（首次加载与用户改价复用同一段），避免出现「金额已变、红字还在」的不一致。

校验放在 `orderPricingService` 而非 `miniOrderController`：§42.3 明确要求，
且「手填价 → 回退零售价」的取值逻辑本来就在该文件里 —— 校验若在别处再推一遍，
两处一旦分叉就会出现「校验用 A、入库用 B」。

**§7.5 自购是否受约束 —— 业务方已确认（2026-09-20）：自购同样受约束。**
`order_scene`（自购 / 代客）**不影响**该校验；前端输入框与下界提示对两种场景完全一致，
服务端 `assertSalesmanMinPrice` 不接收 `order_scene` 参数、不按场景分支。
⚠️ 这条必须保持：若只为「代客下单」设限，任何低价单只要把场景切成「自己订货」即可绕过，规则即失效。
冒烟第 2 节对**两种场景各有一条断言**，并校验两者拒绝文案逐字一致 —— 只测一种的话，
将来若有人给自购加一条放行分支，现有断言仍会全绿。

### 5.5 购物车不存价格

`utils/cart.js` 只存 `productId` / `quantity` / 水票选择。若本地缓存价格，会出现
「加购时 18、下单时档案已改 20，用户看到的还是 18」—— 而且那是**前端算出来的金额**，
直接违反 §22.1 / §22.6。价格一律在下单页向后端取最新档案值。

确认订单页的「合计」标注为**预览**，并明示「最终以服务端计价为准」。

### 5.8 Phase 8b 的「域定式」（后续 10 个域照此办理）

文档 §43 要求 8b「每完成一个业务域即验收一个」。但**逐域验收不等于逐域换写法** ——
否则 17 个域会分裂出 17 套鉴权/幂等/审计写法，评审时无法用同一套眼睛看。故先立定式：

| #   | 约定                                                                                            | 原因                                                                                                                                                                                                                                                                                               |
| --- | ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | 读接口挂 `requireMiniAdmin`；**写**接口再加 `requireMiniActive`                                 | 前者校验「是不是管理员」，后者校验「账号/主体是否被禁用」；管理员账号同样会被禁用（§22.5）                                                                                                                                                                                                         |
| ②   | **不复用 Web 的 `requireAdmin`**                                                                | §22.4：小程序令牌若与 Web 共用校验，管理员身份等于拿到整本 Web 后台                                                                                                                                                                                                                                |
| ③   | 写接口**必须带幂等键**（`clientRequestId`）                                                     | 移动端弱网重试极常见；没有幂等键，一次重试就是两笔账，且两笔都合法、账面看不出异常                                                                                                                                                                                                                 |
| ④   | 幂等指纹走 `utils/requestHash.js`（**哈希后落库**）                                             | `mini_idempotency.request_hash` 是 `varchar(64)`；拼明文串会直接 500（2026-09-21 实测）                                                                                                                                                                                                            |
| ⑤   | 资金动作调**既有账务原语**（`applyExpenseLedger` / `revertExpenseLedger` 等），域控制器只做编排 | §41 头号禁止项：不复制余额与流水的写法；副作用是两端记账方向**物理上不可能分叉**                                                                                                                                                                                                                   |
| ⑥   | 每次写操作**在事务内**落审计（§40），`actor_id = mini:<accountId>`                              | 与 Web 端操作可区分；审计与业务同事务，避免「操作成功但没痕迹」                                                                                                                                                                                                                                    |
| ⑦   | 列表筛选复用既有筛选构造（如 `buildExpenseListWhere`）                                          | 本仓库有「start 含 / end 不含」与「end 含」**两套区间约定**，另写一遍极可能挑错                                                                                                                                                                                                                    |
| ⑧   | 分页 `parseInt` 后内联；下拉一律走专用全量接口                                                  | mysql2 不支持 `LIMIT ?`；分页拉下拉会静默缺项                                                                                                                                                                                                                                                      |
| ⑨   | 与业务无关的积木放 `controllers/mini/admin/_shared.js`                                          | 分页/账户下拉/类别/幂等键校验/错误文案透传——17 份各自实现必然分叉，而分叉形式极难发现                                                                                                                                                                                                              |
| ⑩   | 冒烟**按域分节**写进 `smoke_mini_admin.js`，不按域拆脚本                                        | 每域一个进程会让 `run_smokes.js` 清单失控，且重复登录/建账号/清理；分节仍保留逐域验收能力                                                                                                                                                                                                          |
| ⑪   | 文件类上传**复用 Web 端 multer 中间件与 handler**，只补小程序侧鉴权                             | 目录/命名（UUID）/体积/格式校验只有一份；另写一套必然出现两端规则不一致                                                                                                                                                                                                                            |
| ⑫   | 管理端的配置类写操作，必须有**跨端联动断言**（配置完下游能否看到）                              | 只验"管理端写对了"是不够的：曾出现"界面显示已开启、下游列表却没有"的整链断裂                                                                                                                                                                                                                       |
| ⑬   | **同构域一律走工厂**（`_masterFactory.js`），各域只写一份声明                                   | 四个主数据域的规则完全相同；写四遍的代价不是啰嗦，而是改一处要记得改四处                                                                                                                                                                                                                           |
| ⑰   | **余额字段不接受入参**（编辑接口即便收到 `currentBalance` 也必须忽略）                          | 余额只能由业务单据或转账变动；一旦开放「直接改余额」，账面与流水立刻脱钩且恒等式再也对不上                                                                                                                                                                                                         |
| ⑯   | **改绑定关系必须重签令牌**（`target_id` 变更后旧令牌一律 401）                                  | miniAuth 每请求比对令牌与库中绑定 —— 冒烟里 UPDATE 绑定后不重签，后续请求全 401，看似接口坏了实为令牌失效                                                                                                                                                                                          |
| ⑮   | **错误处理路径本身必须被测到**（业务校验失败 → 走一遍）                                         | 定式积木里 `respondBusinessError` 忘了 import `error`，任何校验失败都抛 ReferenceError → 响应永不返回、客户端挂起到超时；成功路径全绿也测不出来                                                                                                                                                    |
| ⑭   | 接口路径**必须写成字面量**（含配置驱动的页面），不得用拼接/模板串挂载路由                       | `check-api-paths.js` 是正则抽取，看不见拼接 —— 实测造成**整个域的接口在门禁里静默消失**                                                                                                                                                                                                            |
| ⑱   | 小程序侧幂等键的入参**必须是对象**（`{scope, ownerKey, payload}`），不得传字符串                | 传字符串会让 scope/ownerKey/内容指纹一起退化成 `undefined`/常量，于是「内容没变就复用同一个键」被**永久触发**：同一台设备 24h 内的第二次操作会复用上一次的键，被服务端判「同键不同参数」而 400（实测 4 个页面 5 处；接口冒烟测不到 —— 脚本自己生成键）。已加静态门禁（`check-project.js` 第 9 项） |
| ⑲   | 路径拼接前缀（`'/x/' + id`）**不是一条独立调用**，抽取时不得去尾斜杠后单列                      | 实测工资域一次踩出 2 条纯误报（`/admin/salary/payments`、`/admin/salary/worker` 后端未注册）—— 而**误报会训练人忽略告警**，等于让整条门禁失效；已加负向先行断言修正                                                                                                                                |

**为什么第 ⑨ 条是第 2 个域才加的**：第 1 个域（支出）时这些积木只有一份，没有重复就看不出该抽。
做到收入域时同一段代码出现第二遍 —— 这正是「重复的临界点」，此时抽取成本最低、收益最大；
若等到第 5、6 个域再回头统一，就要同时改动已验收的域，风险反而更高。

**另一个只有做第二个域才会暴露的问题**：收入与支出的**记账方向相反**（收入 +、支出 −），
机械照抄会把注释、提示文案、删除确认语全部写反 —— 而这类错误**不影响任何断言通过**
（余额断言若也照抄反了，两边一起错反而自洽）。本次实测在 4 处抓到方向性文案抄反
（列表注释、编辑页注释、编辑页说明文案、删除二次确认文案），已逐一修正并在代码里留下对照表。

### 6.3 已硬化的门禁（「看见了却放行」与「写了却没用」）

前两次属于**同一形态**：缺陷在门禁眼里出现过，但输出仍然是一句「✅ 通过」。

| #   | 缺陷（实测）                                                                                                                                                          | 门禁当时的表现                                                                                                        | 处置                                                                                               |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 1   | `pages/home/index.wxml` 一次编辑漏了开标签、又多出一个 `</view>` → 「主数据」整行失去 `bindtap`（**该域在手机上完全不可达**），其后卡片被挤出容器、`<block>` 提前闭合 | `check-project.js` 的标签闭合检查**发现了**，但只 `warn`，随后照样打印「✅ 结构校验通过」；缺陷因此活过一整个交付批次 | 由 `warn` 提升为 **`fail`**（带行号与「期望闭合谁」），并补双向验证（正常通过 / 注入错位退出码 1） |
| 2   | 4 个页面共 5 处把 `acquireKey('字符串')` 当字符串用（契约是对象）→ 同一设备 24h 内第二次同域操作被服务端判「重复提交内容不一致」而 400                                | **没有任何检查**：只有真机连做两次才会暴露，而接口冒烟自己生成幂等键，根本不走这段页面代码                            | 新增静态检查：`acquireKey(` 后出现引号即判错（注释里的示例不算），并补双向验证                     |

> 教训（与 §5.8 第 ⑭ 条同源）：**门禁必须能拦住它「看见」的问题** ——
> 只报警告的门禁等价于没有门禁，只是多了一行没人读的输出。

**第三类形态 · 门禁误报**（2026-09-22，工资域与水票域各一次）：路径抽取把「拼接前缀」或「三段拼接」当成独立调用，产出后端根本没有的路径 → 报「后端未注册同名路由」，而代码完全正确。修法不是改代码，而是**修门禁本身**：第一次加负向先行断言，结果**被正则回溯绕过**（贪心捕获缩短一位就能满足断言），第二次才改成在归一化里显式判定。⚠️ 两条教训：① 误报与漏报同样有害，误报只会训练人忽略告警；② **「修门禁」也要验证它真的修好了**（注入用例跑一遍：该拦的能拦住，该放行的仍放行）。

**第四类形态 · 守卫写了但恒不生效**（2026-09-22，水票批次删除）：SQL 是
`... WHERE issuance_id IN (${placeholders}) AND status = ?`，参数却写成 `[TICKET_STATUS.USED, ...ids]` ——
绑定错位成 `issuance_id IN (2) AND status = 'WTI...'`，条件**恒不成立**（恒 0 行）。
于是「批次内有已核销票则拒绝删除」这条守卫**完全失效**：含已核销票的批次照样整批删除，
把订单已抵扣的水票一并删掉（订单还在、抵扣记录没了，**且账面看不出异常**）。
它不报错、不抛异常，只是永远放行 —— 比「看见了却放行」更隐蔽的一层。
新增增量红线 **R11** 静态识别该形态（`IN (${...})` 在前、其后还有 `?` 时，参数数组首位必须是展开），并按老规矩双向验证：错误顺序拦下、两处正确写法（`SET status = ? WHERE ... IN (...)`）放行。

**第五类形态 · 路由名撞车：注册两次不报错，只静默命中先注册的那个**（2026-09-22，账号管理域）：
新域的 5 条路由写成 `/admin/accounts*`，而该前缀**已属「公司资金账户」域（第 10 域）** ——
Express 对同名路由注册两次**不报错**，请求静默落到**先注册**的那个：列表接口返回的是
**公司资金账户**、`DELETE /admin/accounts/:id` 删的是公司账户、`/options` 给的是公司账户下拉。
**所有接口都返回 200**，没有任何异常信号（状态码、日志、页面都正常）。
发现它的是**列表形状断言**（断言返回行里有 `role`/`phoneMasked` 这类字段）——
只验「200 + 有 list」会全绿通过。
⇒ 两条纪律：① **新增路由前先 grep 该路径前缀**；② **列表类接口必须断言「行的形状」**，
不能只断言「接口通」。这也是本域首版唯一被拦住的问题，属「接口冒烟」不可替代的价值。
