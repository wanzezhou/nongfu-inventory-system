# 微信订货小程序方案（V1.0）评审意见

> 评审日期：2026-09-20　|　评审对象：`nongfu-mini-program-dev-spec-v1.0.md`（49 章 / 2.4 万字）
> 评审方式：**逐条对现有代码核实**（不是就文档读文档）。所有结论附 `文件:行号` 证据。
> 评审结论：**方向正确，可进入开发拆解；但必须先修 5 处事实错误 + 补 4 处安全缺口**。

---

## 〇、总评

这份方案的质量**高于同类文档的平均水平**，尤其三点做得对：

1. **拒绝建第二套业务系统**（订单/定价/库存/水票/营收全部要求复用），并点名了正确的接入点（`orderPricingService.js`、`utils/revenueExpr.js`）。
2. **安全姿态正确**：不信任前端金额、不信任 `buyer_id`、令牌换身份、幂等键、事务边界、对账恒等式。
3. **区分了「充值」与「主营业务收入」**（§19.1）——这是绝大多数同类方案会算错的地方：预收款不能重复确认收入。

**但它的「现状描述」有 5 处与真实代码不符**，其中 2 处会直接导致实现走偏（详见第二节）。另有 **4 处安全缺口文档完全没覆盖**，而它们都踩在本仓库已经付出过代价的地方（第三节）。

## 二、与代码不符的 5 处（必须改，否则实现会走偏）

### 2.1 ⚠️ `mini_accounts` 不是「现成基础设施」，而是**上一版小程序废弃后的残留**

文档 §0 / §4.1 把它当作既有能力来复用（"现有仓库的 `mini_accounts` 已存在，并包含微信 openid、角色和关联实体 target_id"）。**表在，但生态已死**：

| 事实                                                              | 证据                                                                                                                                                |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 表存在，15 列，`role enum('admin','worker','station','salesman')` | DDL 见 `full_schema_data.sql`                                                                                                                       |
| **全仓库无一行代码读写它**                                        | 已全树扫描 `backend/src` + `frontend/src`：`mini_accounts` / `openid` **零命中**                                                                    |
| 上一版小程序**已于 2026-08-23 彻底删除**                          | `docs/交接文档.md`：「原微信小程序已于 2026-08-23 彻底删除」                                                                                        |
| `/mini/*` 接口已整体移除                                          | `docs/项目概览.md`；`backend/src/routes/` 21 个路由文件**无 mini***                                                                                 |
| 历史曾有 **147 个 mini 相关路径**，现全部不存在                   | git 历史：`mini-program/`（原生 WXML）、`controllers/mini/*`、`middleware/miniAuth.js`、`miniRole.js`、`routes/miniRoutes.js`、`smoke_mini_rbac.js` |
| 删除提交                                                          | `fd0e351 彻底删除小程序 + 删除订单状态字段(canceled_at 替代)`                                                                                       |
| **表内还有 4 条 `status=1`（启用）的种子账号**                    | `openid` 分别为 `seed_admin`(role=admin) / `seed_worker` / `seed_station` / `seed_salesman`，均带 bcrypt 散列                                       |
| 另有 `sms_codes` 孤儿表（手机验证码登录）                         | 表在，无代码引用；同属上一版残留                                                                                                                    |

**为什么这不是「小瑕疵」**：

- 文档基于「已有基础设施」的假设，**低估了 Phase 1 的工作量**——真实起点是「一堆需要先决策、清理、甚至重建的遗留物」。
- 4 条**启用中**的占位账号（其中一条 `role=admin`）与 `openid` 唯一索引共存：新版若沿用「手机号匹配 + 绑定」逻辑，或若绑定流程出现兜底分支，它们就是**可被触达的既存账号**。上线前必须显式清理，不能靠"反正没人用"。
- 文档没有回答**上一版为什么死**。旧版本是「原生 WXML + 4 角色 + 19 页 + 管理员全覆盖」，2026-08-12 立项、08-23 删除，**存活 11 天**。这一版的 §5.3 同样是「管理员覆盖 Web 全部业务能力」——**最大的工作量项与上一版的死因高度重合**，值得先写一段复盘（见第四.4）。

### 2.2 §12.1「分销配送费自动带出商品档案的单件值」是**前端行为**，服务端并不校验

文档把它当作可依赖的系统性质。实际：

- 前端确实自动带出**并换算**：`WaterTicketManage.vue:227-228/232` —— `unitDeliveryFee = product.distributionDeliveryFee`，然后 `distributionDeliveryFee = unitDeliveryFee × quantity`
- 后端**原样入库、只校验 ≥0**：`waterTicketController.js:27`（取前端值）、`:30`（只校验 `>= 0`）、`:58`（直接写入 `distribution_delivery_fee`）

**在当前模型下这没错**（只是个记录数字）。但本方案的 **§12 要让它变成钱**（钱包积分）——同一个「只校验 ≥0」的入口，就会变成**「前端传多少，公司就欠水站多少积分」**。这恰好违反文档自己在 §22.1 立的原则（不能信任前端金额），却没在 §12 应用。

➡️ 必须补：`unit_distribution_fee` **一律由服务端从 `products.distribution_delivery_fee` 重取**，前端值只作展示。

### 2.3 §12.2 / §20.4 的条件句「如果现有字段已作为历史总额使用…」——**可以给出确定答案**

文档谨慎地留了个条件分叉。核实结果：

> **`water_ticket_issuance.distribution_delivery_fee` 存的是【总额】，不是单件值。**

证据链：

1. 该表已有独立 `quantity` 列（同表并列，见 DDL）；
2. 前端在数量变化时**重算**：`distributionDeliveryFee = unitDeliveryFee × quantity`（`WaterTicketManage.vue:228` 初始、`:232` 数量变更时）；
3. 后端不做任何反算。

**因此文档要求拆分「单位值 / 总额」不是设计偏好，而是硬需求**，并且有一个文档没说的更强理由：

> **单件值当前从不落库。** §12.7「作废 1 张票 → 扣回 3 积分」需要**单件值**，而库里只有总额——只能靠 `总额 ÷ 数量` 反推。一旦 §12.6 允许调整数量、或历史数据出现除不尽的情况，反推就会引入误差。**必须新增并持久化 `distribution_delivery_fee_unit`。**

➡️ 结论：保留 `distribution_delivery_fee`（总额，向后兼容），**新增单位值列**；总额列可作为冗余或改由代码计算（二选一，但要在文档里定死）。

### 2.4 §6.2 新增 `order_source` —— 与既有 `platform_type` 语义重叠

`orders` 里**已存在** `platform_type` 与 `platform_order_no`（`orderController.js:280/289` 写入、`:565-566` 更新、`:52` 回显给前端），且经 `orderPricingService.normalizeOrderPayload` 透传（`:36`）。但**前端从不读取/展示**——实际是「写进去就没人看的字段」。

文档新增 `order_source`（WEB / MINI_PROGRAM）会让订单表出现**第三个来源语义字段**。

➡️ 二选一并写进文档：(a) 复用 `platform_type`（定义取值 + 补前端展示）；(b) 新增 `order_source` 并**明确 `platform_type` 的去留**（建议标注为历史遗留、不再写入）。**不要留三个表意相近的字段。**

### 2.5 文档的「表数量」参照可能过期

`AGENTS.md` 仍写「MySQL（30 张表）」，而 `database/full_schema_data.sql` 实际 **35 张**。文档的 DB 变更章节应基于 35 现状编写（避免新增表后文档与库对不上）。

## 三、文档完全没覆盖的 4 处安全/一致性缺口（最需要补的部分）

### 3.1 🔴 令牌越权：小程序 admin 令牌 ≈ Web 全权令牌

现状鉴权极简（`backend/src/middleware/auth.js` 全文 43 行）：

- `auth`：只做 `jwt.verify(token, JWT_SECRET)`，然后 `req.user = decoded`
- `requireAdmin`：**只看 `req.user.role === 'admin'`**
- Web 登录签发的 payload 固定为 `{ id, username, role }`（`authController.js:40-43`）
- **没有 RBAC**——全系统只有「已登录」与「admin」两道门

如果小程序的 JWT 使用**同一个 `JWT_SECRET`**、payload 形状相同、且 `role` 取自 `mini_accounts`（枚举里**就有 `admin`**，且现存种子 `seed_admin` 正是 `role=admin`），那么：

> **小程序管理员令牌可以直接通过所有 Web 管理接口的 `requireAdmin`。**

而文档 §5.3 恰好要求「管理员覆盖 Web 全部业务能力」——**这条路是设计上被默认打开的，文档却没有任何令牌契约的规定**。

➡️ 必须补：小程序令牌使用**独立密钥或独立 audience/issuer**，配独立的 `miniAuth` 中间件；并写明「小程序令牌**不得**通过 Web 的 `requireAdmin`」。上一版已有此设计的雏形（历史文件 `middleware/miniAuth.js` + `miniRole.js`），可直接沿用其思路，但要在文档里成文。

### 3.2 🔴 §4.5「禁用后禁止登录/下单/充值/消费」目前**做不到**

`auth` 中间件**不查数据库 `status`**，只验签名。JWT 有有效期（`JWT_EXPIRES`），意味着：

> 一个被禁用的小程序账号，在令牌过期前**可以继续下单、充值、消费**。

➡️ 必须补：每次请求校验 `mini_accounts.status`（或短有效期令牌 + 刷新令牌），并把「禁用 → 逐一拦截」写成可测的验收项（文档 §44 目前无此项）。

### 3.3 🟠 两套资金体系并存，钱包侧必须复刻「三联事务 + 撤销回补」

现有资金体系是 `finance_accounts` + `finance_transactions`，遵守仓库铁律：**业务记录 + 余额 + 流水同一事务**；撤销类操作**必须回补余额并写流水**；且**停用账户也必须满足「余额 = 期初 + 流水净额」**。

文档新增 `wallet_accounts` + `wallet_transactions`，§11.5 提了恒等式、§11.6 提了 `FOR UPDATE`，但**没有把上述纪律显式继承过来**，尤其遗漏：

- **撤销类必须 `−amount`**（收入方向的撤销写成 `+` 会「越撤越多」，而恒等式可能看起来仍然成立——这是本仓库踩过的坑）
- **钱包也要接受「停用账户恒等式仍成立」的约束**（`mini_accounts.status=0` / `wallet_accounts.status=0` 时）
- 订单被删/改时的钱包冲正，需与既有 `restoreSalesEffects` 同事务，不能各写一套

另有一个文档未提的既有复杂度：**type 2 的营收入账本就拆两笔**（水票抵扣 → 农夫上单账户；未抵扣 → 晟之溪公户，见 `orderController.js:356-365`）。小程序水站订单会**继承**这条拆分逻辑，同时还多一笔钱包扣减——文档 §24.2 的事务清单里没有体现这层。

### 3.4 🟡 微信充值只走「微信支付」一条路，但**外部资质是最长依赖**

文档 §25 已正确列为前置条件（这很好）。补充两点风险：

- 小程序支付要求**已认证主体**、类目、商户号、AppID 授权绑定、可能触发**交易类发货管理**——这些**不受开发进度控制**。文档把 Phase 6 排在 Phase 5 之后，但**资质审批应与 Phase 1 并行启动**，否则它会成为唯一的阻塞项。
- 若资质未就绪，**钱包充值**这条链路（含积分钱包的全部正向来源）就无法端到端验证。建议文档明确一个「无充值可开发」的降级路径：管理员手工调增积分（§18）先行可用，业务订单链路即可先跑通。

## 五、Phase 顺序的 3 条调整建议

1. **Phase 0（资质）应与 Phase 1 并行启动，不能串行等待**——它是唯一不受开发进度控制的外部依赖（详见 3.4）。
2. **Phase 8 拆成 8a / 8b**：8a = 只读看板（必需，工作量小）；8b = 完整管理能力（延后，另行评估）。理由见第四.3。
3. **Phase 7（水票积分）需要独立的风险预案**：它要求**改造现有 Web 功能**（§12.9 停用 `/adjust-delivery-fee` 与 `/adjust-station-delivery-fee` 的"直接改历史金额"能力）。这是**唯一会破坏现有已上线功能**的一期，需要：兼容方案 + 迁移脚本 + 现有水票冒烟（`smoke_barrel.js` 等）回归 + 明确回滚路径。

## 六、建议补充的章节

1. **现状核实附录** —— 本文第一、二节可直接并入，带 `文件:行号`，避免后续 AI/开发者再凭检索结论开工。
2. **身份与令牌规范** —— Web / 小程序令牌的密钥、payload、中间件、越权边界（补 3.1）。
3. **钱包资金纪律** —— 显式继承 AGENTS.md 的资金三联事务 / 撤销回补 / 停用账户恒等式（补 3.3）。
4. **对账取数单源** —— §19.4 / §38 / §39 的三个对账视图应抽成**一个 service**（与既有 `services/otherLedgerSummary.js` 同模式），**禁止在 controller 里各写一份公式**。这是本仓库的口径分叉高危区。
5. **幂等键的生命周期** —— §23 说 `buyer_id + client_request_id` 唯一，但没定义：谁生成、App 重启/换设备后如何保持、重试窗口多久、冲突时返回什么。这决定了「订单扣款成功但前端超时」这类异常能否安全恢复（§45 已列为必测项，但没有答案）。
6. **个人信息合规** —— `openid` / 手机号 / 收货地址均属个人信息；小程序需**隐私协议 + 授权时机 + 最小必要**。另需与仓库已知的 PII 议题（`full_schema_data.sql`）保持口径一致。
7. **可测的验收数字** —— 文档 §44 的验收标准写得很好（可执行），建议再补「基线数字」，与仓库既有规范对齐：每个改口径的改动都要有断言，且**断言不得空转**（数据全 0 时恒等式会"通过"却什么都没测）。
