# 代码审查流程

> 版本：v1.0（2026-09-18 制定）
> 配套：《代码审查标准.md》（判断依据）、《代码审查-基线风险发现.md》（本轮审查结论）
> 定位：本文件规定**谁在什么时机按什么步骤审**，以及每一步的进入/退出条件。

---

## 一、现状诊断（为什么流程要这样设计）

勘察结论（2026-09-18）：

| 项 | 现状 | 结论 |
|----|------|------|
| 分支模型 | 单 `master`，132 commit 全直推，有 `origin`（GitHub）但无 PR 实践 | 🔴 无评审发生的场所 |
| 静态检查 | **零** ESLint / Prettier / EditorConfig | 🔴 无机器闸门 |
| CI | 无 `.github/` 目录 | 🔴 无合并前门禁 |
| commit 规范 | 人工执行得很好（`fix(router): 修「删零售机把量贩机删了」…`），但无 commitlint 兜底 | 🟡 规范靠自觉 |
| 测试资产 | 后端 40 个 `smoke_*.js`（含断言计数）、前端 2 个静态门禁 + ui-smoke，**均有退出码** | ✅ 资产齐备，只需接线 |
| PR 模板 / CODEOWNERS | 无 | 🔴 无评审清单载体 |

**关键判断**：这个项目不缺验证手段，缺的是**把验证手段强制接到合并动作上**。`backend/scripts/check_frontend_tokens.js` 的注释里甚至已经写了"CI/冒烟流程可用退出码判断"——说明当初就是这么计划的，只是没做。所以本流程的设计重点是**接线**，不是发明。

## 二、角色与职责

| 角色 | 职责 | 本项目对应 |
|------|------|-----------|
| **作者（含 AI）** | 自审、提供证据、回答三问、响应评审意见 | 提 PR 的开发者 + 生成代码的 AI |
| **评审者** | 按标准判 S1–S4，机器查不到的语义问题 | 至少 1 名熟悉对应模块的开发者 |
| **领域守门人** | 对特定目录的改动有最终否决权 | 见 `.github/CODEOWNERS` |
| **合并者** | 确认全部闸门通过后合并 | 作者本人可合（通过闸门后） |

**分工原则**：

- **机器负责**：格式、未使用变量、空 catch、mock 兜底、`SELECT *`、硬编码上限、色值 token、未声明引用、大文件、密钥泄露。
- **人负责**：业务语义、失败路径的行为选择、口径唯一性、字段真实存在性、并发与边界、可维护性判断。
- **AI 不负责**：AI 不参与评审自己的产出，其自述结论不构成证据。

## 三、分支与提交模型

### 3.1 分支

```
master                  ← 只接受通过全部门禁的合并，禁止直接 push
  └── feat/xxx          功能
  └── fix/xxx           缺陷修复
  └── refactor/xxx      重构（不含行为变更）
  └── chore/xxx         杂务（依赖、配置、文档）
```

**硬性要求**：

- `master` 开启分支保护，禁止直接 push、禁止 force push
- 一个分支 = 一件事。分支存活期不超过 5 天，超过必须拆分或说明
- 🟡 **AI 生成的改动必须小步**：单 PR 建议 ≤ 400 行 diff（不含生成产物/锁文件）。> 800 行的 AI 产出 PR，评审者应当**直接要求拆分**而非硬审

### 3.2 提交信息（沿用现有习惯，加机器兜底）

格式：`type(scope): 中文描述`

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（无行为变更） |
| `perf` | 性能优化 |
| `style` | 样式/格式（不含逻辑） |
| `docs` | 文档 |
| `test` | 测试/冒烟 |
| `chore` | 构建、依赖、配置 |
| `data` | 数据/迁移 |

- 描述用**中文**，说清"改了什么"；涉及历史缺陷的标注编号（如 `fix(order): 修水票未还原（F3）`）
- `type!` 表示破坏性变更（历史已有先例：`style(theme)!`）
- 由 `.husky/commit-msg` + commitlint 校验

## 四、五道闸门

```
                 ┌─────────────────────────────────────────────┐
  需求/意图 ───► │ G0 意图对齐（写清范围与验收）                  │
                 └──────────────────┬──────────────────────────┘
                                    ▼
                 ┌─────────────────────────────────────────────┐
  写码 ────────► │ G1 作者自审（AI 三问 + 速查卡）               │
                 └──────────────────┬──────────────────────────┘
                                    ▼
                 ┌─────────────────────────────────────────────┐
  提交 ────────► │ G2 机器门禁（本地 pre-commit + PR CI）         │──失败─► 打回
                 └──────────────────┬──────────────────────────┘
                                    ▼
                 ┌─────────────────────────────────────────────┐
  评审 ────────► │ G3 同行评审（按标准判级，一次性给全）          │──S1───► 阻断
                 └──────────────────┬──────────────────────────┘
                                    ▼
                 ┌─────────────────────────────────────────────┐
  合并 ────────► │ G4 证据与回归（冒烟 + 文档同步 + 合并）        │
                 └─────────────────────────────────────────────┘
```

### G0 — 意图对齐

**进入条件**：有一个明确要改的东西。

**退出条件**（写进 PR 描述，或在动手前口头确认）：

1. 这次要改什么（一句话）
2. 验收方式是什么（跑哪个冒烟 / 看哪个页面 / 对哪个数）
3. 是否触及 I1–I5（不变量）
4. 明确**不做什么**（防止 AI 顺手重构）

> 🔴 **AI 场景特别重要**：不给 AI 划边界，它会"顺手优化"无关代码，把真实缺陷埋在大量无关 diff 里。

### G1 — 作者自审

**动作**（按顺序，不可跳）：

1. **读自己的 diff**，逐行。不读 diff 直接提 PR 的自审无效。
2. 跑《标准》附录 A 的**速查卡**。
3. 回答 **AI 三问**（问字段 / 问失败 / 问口径），写进 PR 描述。
4. **自查同类扩散**：本次改动是否有"复制到别处"的痕迹？所有同类位置是否同步？
5. 跑相关冒烟，把输出**原样粘贴**。

**退出条件**：速查卡全勾 + 三问有答案 + 冒烟有输出。

### G2 — 机器门禁

**两级**：

**本地（`pre-commit`，秒级，只查改动文件）**

| 检查 | 工具 |
|------|------|
| 格式化 | Prettier（`--write` 后重新 add） |
| 静态缺陷 | ESLint（改动文件） |
| **项目红线** | `scripts/check-diff-hazards.mjs --staged`（项目史踩过的坑，只判新增行） |
| 前端引用检查 | `check-script-refs.mjs`（改动 .vue 时） |
| 色值 token | `check_frontend_tokens.js`（改动 `.vue`/`.css` 时） |
| 敏感文件 | 阻断 `.env`、`backend/uploads/`、`商品档案/`、`database/backup_*.sql` |

**PR CI（`gh` workflow，全量）**

| Job | 内容 |
|-----|------|
| `hazard-scan` | `scripts/check-diff-hazards.mjs`（对比 PR base sha，只判改动新增行） |
| `lint` | ESLint 全仓 + Prettier `--check` |
| `static-gates` | `check-script-refs.mjs`、`check_frontend_tokens.js` |
| `build` | 前端 `vite build`（防语法/导入错误进主干） |
| `diff-guard` | 改动规模守卫（>800 行告警）+ 禁止提交项检查 |

> 🔑 **门禁可执行性的关键设计**：红线扫描器**只对「本次改动新增的行」判定**。全仓当前有 186 处存量命中（其中 error 级 152 处，见《基线风险发现》），若要求"全绿才可合并"，团队会在第二天就把闸门关掉。增量判定的效果是：**存量作为基线只统计、不阻断；新增违规立即阻断**——存量不会因新代码加入而变差（棘轮效应），同时新增代码被拦住。

**退出条件**：全绿。**红灯不允许"先合后修"。**

> ⚠️ 冒烟脚本需要 MySQL，不进 PR CI（成本高）。冒烟通过由作者在 G1/G4 提供**输出证据**，CI 只做静态门禁。

### G3 — 同行评审

**评审者动作**：

1. 先读 PR 描述与三问答案，再读 diff（顺序很重要——先看代码容易被"看起来对"带偏）
2. 按《标准》第二–六章判级，**一次性给全所有意见**（禁止挤牙膏式多轮）
3. 每条意见用《标准》第四章的格式：

```
🔴 S1 · 静默错数据：硬编码取数上限
CostSummary.vue:169 `pageSize: 500`

为什么：其他支出记录超过 500 条时，成本汇总静默少算，属资金口径错误。

建议：改为服务端聚合接口返回汇总值，或加大上限并在超限时显式提示。
```

4. 明确结论：`通过` / `需修改（含 S1-S2 列表）` / `打回重做`

**SLA（建议）**：

| PR 规模 | 首次响应 |
|--------|---------|
| ≤ 100 行 | 4 工作小时内 |
| ≤ 400 行 | 1 个工作日 |
| > 400 行 | 要求拆分，或约定时间 |

**评审反模式（禁止）**：

| 反模式 | 为什么禁止 |
|--------|-----------|
| "整体看着没问题" | 无级别的意见等于没审 |
| 只提格式问题 | 格式交给 Prettier，人的注意力是稀缺资源 |
| 挤牙膏式多轮提意见 | 消耗作者信任，掩盖真实缺陷 |
| 只看 diff 不看调用链 | AI 代码的字段幻觉往往在跨文件时才暴露 |
| 以"AI 应该没问题"为由跳过验证 | AI 自述不是证据 |
| 顺手要求重构无关代码 | 制造范围蔓延，混入新风险 |

### G4 — 证据与回归

**合并前最后确认**：

- [ ] G2 全绿（附 CI 链接）
- [ ] 相关冒烟输出已粘贴，断言计数与基线一致（如 `smoke_order_pricing.js` 基线 40/40）
- [ ] 触及 I1–I5 的改动有守恒验证
- [ ] UI 改动有浏览器证据
- [ ] `docs/项目概览.md` 已同步（〇节变更记录 + 对应功能描述）
- [ ] 新发现的陷阱已追加到 `AGENTS.md` 的"已知陷阱"
- [ ] 无遗留 S1/S2；S3 已登记 Issue

**合并方式**：Squash merge（保持 `master` 历史一条一事的可读性）。合并后删除分支。

## 五、严重度处置矩阵

| 级别 | 是否阻断合并 | 谁决定 | 记录位置 |
|------|------------|-------|---------|
| S1 | ✅ 是，无豁免 | 评审者 / 领域守门人 | PR 内，修完关闭 |
| S2 | ✅ 是（或转 Issue） | 评审者 | PR 内 + Issue |
| S3 | ❌ 否 | 作者酌情 | GitHub Issue |
| S4 | ❌ 否 | 作者酌情 | 仅评论 |

### 豁免机制（唯一通道）

S1 不可豁免。S2 若确需延后，必须在 PR 描述中写明：

```
延后项：<内容>
原因：<为什么本 PR 内不能修>
风险：<不修会怎样，最坏情况>
Issue：#<编号>
补修期限：<日期>
```

无 Issue 号的延后一律视为未处理。

## 六、度量指标

**周度**（从 git + CI 自动统计，不手工填表）：

| 指标 | 含义 | 目标趋势 |
|------|------|---------|
| PR 平均规模（行） | AI 产出粒度是否收敛 | ↓ |
| PR 平均存活时长 | 流程摩擦 | ↓ 且 5 天内 |
| 首次评审响应时长 | SLA 达成率 | 达成 ≥ 90% |
| CI 首次通过率 | 自审质量 | ↑ |
| S1 缺陷数 / PR | 最关键的指标 | → 0 |
| 冒烟脚本数量 | 回归防护是否同步增长 | ↑（只增不减） |

**月度**：

- 复发缺陷统计：本次修复的缺陷，是否与历史缺陷同类？若同类复发 ≥ 2 次，说明**标准或机器门禁有缺口**，应补一条 ESLint 规则或清单项，而不是再修一次。
- **把这个循环写死在流程里**：
  ```
  发现缺陷 → 修复 → 判断能否机器化 → 能则补 ESLint 规则 / 能则补清单项
                                      → 都不能则补 AGENTS.md 已知陷阱
  ```
  历史 F1/F2/F6 复发（本次在 OrderFormDialog 发现 F6 同类 5 处）证明：**不补门禁的修复会复发。**

## 七、紧急通道（hotfix）

仅限生产不可用 / 资损正在发生。

- 允许直接从 `master` 拉 `hotfix/xxx`，允许简化 G0（口头说明范围）
- **G2 机器门禁不可跳过**（静态检查秒级，没有跳过的理由）
- **G3 可简化为单人快速评审**（评审者必须在 30 分钟内响应）
- **G4 沉淀**：hotfix 合并后 24 小时内必须补 PR 描述、补冒烟、补文档同步、回答三问
- 事后 3 个工作日内在周会复盘：这个缺陷为什么没被现有门禁拦住？补哪条？

## 八、落地路线（接线步骤）

工具链配置已随本流程一并落地：

| 文件 | 作用 |
|------|------|
| `eslint.config.mjs` | ESLint 9 扁平配置，含项目红线规则 R1–R7（前后端共用） |
| `scripts/check-diff-hazards.mjs` | **增量红线扫描器**：只判新增行，是门禁能被长期保留的关键 |
| `.prettierrc.json` / `frontend/.prettierrc.json` | 格式化（后端带分号、前端无分号，沿用现有风格，避免全量 diff） |
| `.prettierignore` | 排除 dump、备份、生成物 |
| `.editorconfig` | 编辑器层缩进/换行一致性 |
| `.commitlintrc.json` | 提交信息规范（type/scope/subject） |
| `.lintstagedrc.json` | 只对暂存文件跑 lint/format，保证 pre-commit 在秒级 |
| `.husky/pre-commit` | 敏感文件阻断 + 格式 + 红线扫描 + 前端静态门禁 |
| `.husky/commit-msg` | commitlint 校验 |
| `.github/pull_request_template.md` | 与五道闸门对齐的 PR 模板（含 AI 三问） |
| `.github/CODEOWNERS` | 领域守门人（不可变式核心文件的高风险标注） |
| `.github/workflows/code-review-gate.yml` | PR CI：红线扫描 / lint / 静态门禁 / 构建 / 规模守卫 |

**配置只是文件，需要安装依赖才生效。**

### 第一步：安装工具链（约 3 分钟）

```bash
# 在仓库根目录执行
npm init -y                                  # 若根目录无 package.json
npm i -D eslint@^9 @eslint/js globals eslint-plugin-vue vue-eslint-parser \
         prettier@^3 \
         husky@^9 lint-staged@^15 \
         @commitlint/cli @commitlint/config-conventional
npx husky init
```

> 或直接在现有 `frontend/package.json` / `backend/package.json` 里各自安装对应子集——但**根目录统一**更适合本项目（跨前后端的规则可以共享）。

### 第二步：验证门禁真的会拦人

```bash
# ① 红线扫描器（现在就能跑，无需安装任何依赖）
node scripts/check-diff-hazards.mjs --all      # 全仓基线：应为 186 处 / error 152 处
node scripts/check-diff-hazards.mjs --staged   # 暂存区判定（pre-commit 用）

# ② 仓库原有静态门禁（现在就能跑）
node frontend/scripts/check-script-refs.mjs    # 应为 0 退出码
node backend/scripts/check_frontend_tokens.js  # 应为 0 退出码

# ③ 安装依赖后验证 lint（首次必然有告警，属预期）
npx eslint .
npx prettier --check .
```

### 第三步：基线豁免（重要——防止门禁一上线就被关掉）

首次全量 lint 必然有大量历史告警。**不要**为了"绿灯"把规则关了，而是：

1. 记录首次基线数字（如 `X errors / Y warnings`）
2. 对**历史遗留**用 `.eslintignore` 或 per-file `/* eslint-disable */`（**须带注释说明豁免原因与计划**）
3. 对**新增代码**用 `--max-warnings` 卡住，逐周收紧阈值
4. 在 `docs/项目概览.md` 记录基线与收紧计划

### 第四步：开启 `master` 分支保护

- 禁止直接 push、禁止 force push
- 要求 `lint` + `static-gates` 两个 CI job 通过后才可合并
- 本次为单人项目时可先只开"禁止 force push + 要求 CI 通过"，评审人自任

### 第五步：建立节奏

| 频率 | 事项 |
|------|------|
| 每次改动 | 五道闸门 |
| 每周 | 看 6 个度量指标；CI 红灯原因归纳 |
| 每月 | 复发缺陷分析 → 补门禁；`AGENTS.md` 已知陷阱增补；阈值收紧 |
| 每季 | 标准本身复审（哪些条款从未触发？哪些在制造摩擦？） |

## 附录：PR 描述模板

已落地在 `.github/pull_request_template.md`，结构与 G0–G4 对齐：范围 → 不变量影响 → AI 三问 → 证据 → 检查清单。
