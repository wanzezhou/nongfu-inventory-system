# 代码审查标准

> 版本：v1.0（2026-09-18 制定）　|　适用：农夫山泉经销商进销存系统全仓（backend / frontend / database / scripts）
> 配套：《代码审查流程.md》（怎么审）、《代码审查-基线风险发现.md》（本轮审查结论）
> 定位：本文件是**判断依据**——一条改动"能不能合"，看这里；"按什么步骤审"，看《流程》。

## 〇、这份标准解决什么问题

系统由 AI 高频生成代码，单次产出质量不差（事务、锁、参数化 SQL 都做得到），但**质量的方差很大**，且病灶高度集中、反复复发。本标准的编写原则是：

1. **只写这个项目真正踩过的坑**，不抄通用最佳实践清单。每一条红线都能指向一次真实事故或一次已修复的历史缺陷。
2. **能用机器判的绝不用人眼看**。能落成 ESLint 规则的，就不写进评审清单。
3. **判"错"优先于判"丑"**。格式问题交给 Prettier，人只审机器看不懂的语义。

**已确认的核心事实**（决定了本标准的重心）：

- 历史债务报告（`docs/技术债务审查报告.md`）中 P0–P3 共 43 项**已全部闭环**——也就是说，这个团队有能力修，问题不在能力，在**没有机制阻止复发**。
- 已验证的复发案例：历史缺陷 F6 修的是 `OrderList.vue` 商品下拉取前 100 条，而同一次会话生成的 `OrderFormDialog.vue` 里至今仍有 **5 处** `pageSize: 100`（401/402/454/576/577 行）。**同一个坑，换了个文件又长出来了。**
- 仓库当前 **零 ESLint、零 Prettier、零 commit 规范、零 CI、零 PR 模板**，132 个 commit 全部直推 `master`。AI 生成的代码没有任何机器闸门。

## 一、不可变式（Invariants）—— 违反即阻断，不接受讨论

以下五条是本系统的资金/库存/账务守恒关系。任何改动只要可能破坏其中一条，**必须**在 PR 中显式说明如何保证不破，并提供验证证据。

| # | 不可变式 | 含义 | 已有保障 |
|---|---------|------|---------|
| I1 | **资金守恒** | 任何账户余额变动 = 一条 `finance_transactions` 流水，`balance_before`/`balance_after` 成对且与 `finance_accounts.current_balance` 一致 | 三联事务规范（`.workbuddy/memory/MEMORY.md` 第一条） |
| I2 | **库存守恒** | 入库 / 出库 / 盘库 / 订单扣减 四条路径对同一 `inventory.quantity` 的净变化之和 = 台账记录之和 | `FOR UPDATE` 行锁 + `stock_in_records`/`stock_out_records` |
| I3 | **水票守恒** | 水票状态迁移可逆：订单取消/修改必须把已核销水票还原为可用 | `water_ticket.status` + `orderPricingService.restoreSalesEffects` |
| I4 | **订单可逆** | 取消/删除订单必须完整回滚其全部副作用（库存、水站欠款、水票、营收流水） | `orderPricingService` 四件套统一出口 |
| I5 | **口径唯一** | 营收/成本口径只有一处实现，前端只展示不计算 | `utils/revenueExpr.js`（营收唯一来源） |

🔴 **阻断条件**：改动触及 I1–I5 任一项，而 PR 描述中未写明"如何保证不破坏"，或未提供对应冒烟脚本的运行结果。

## 二、严重度定义与处置

| 级别 | 名称 | 判定标准 | 处置 |
|------|------|---------|------|
| **S1** | 阻断 | 破坏 I1–I5；安全漏洞；静默错数据；生产不可用 | 必须修复，不允许"下个 PR 再修"，不允许豁免 |
| **S2** | 需修 | 明确的逻辑缺陷；失败路径误报成功；无边界校验；新增 N+1 | 本 PR 内修复，或转 Issue 并在 PR 中记录 Issue 号 |
| **S3** | 建议 | 可维护性问题；重复实现；命名不清；缺注释 | 可延后，但需在 PR 中登记 |
| **S4** | 优化 | 风格、替代方案探讨 | 仅评论，不阻塞 |

评审意见必须标注级别。**没有级别标记的意见，作者有权不处理。**

## 三、通用红线（S1，机器优先拦截）

这些已尽量落成 ESLint 规则（见根目录 `eslint.config.mjs`），机器能拦的不要靠人。

| # | 红线 | 为什么 | 历史出处 |
|---|------|--------|---------|
| R1 | **禁止 mock / 假数据兜底**。接口失败必须展示空表 + 报错，禁止 `generateMockData()` 之类把伪造业务数据塞进表格 | 用户会把测试假单当真实数据用于备货对账，比报错危险得多 | 历史 F2（6 个页面） |
| R2 | **禁止空 catch、禁止"catch 里报成功"**。`catch {}`、`catch(e){}`、以及 catch 分支执行 `ElMessage.success` 一律阻断 | 操作失败而用户以为成功，台账与实际脱节 | 历史 F1（出库失败报成功） |
| R3 | **禁止 `SELECT *`**，必须显式列出字段 | 拖网络与内存；列变更时隐式耦合；无法做覆盖索引优化 | 历史 37 处 |
| R4 | **禁止把 `err.message` / SQL 原文返回给客户端**，一律经 `utils/response.js` 输出固定文案，原文只进日志 | 泄露表结构、文件路径、库名 | 历史 S7 |
| R5 | **禁止硬编码取数上限**（`pageSize: 999`、`LIMIT 500` 这类魔数）。分页接口必须有明确上限语义 + 超限提示；下拉类数据必须走专用轻量接口或远程搜索 | 超限即静默少算，属**静默错数据**（S1） | 本轮新增发现，见《基线风险发现》#1 |
| R6 | **禁止绕过分层写业务**。订单定价/扣库存/水票核销/副作用恢复必须走 `services/orderPricingService.js`；营收口径必须用 `utils/revenueExpr.js` | 一处漏改即口径分裂 | 历史 D1、A6 |
| R7 | **禁止在 HTTP 层新增第二套错误语义**。业务错误一律 `utils/response.js` 的 `error(res, msg, code)`；新增鉴权中间件必须与 `middleware/auth.js` 的口径一致 | 双语义导致监控与前端处理漏判 | 见《基线风险发现》#7 |

## 四、AI 生成代码专项规则 ★ 核心章节

### 4.1 为什么 AI 代码需要单独一套规则

AI 生成代码的失败模式**和人类不一样**。人写错通常是"不会"，AI 写错是"看起来太对了"——它的输出在结构、命名、注释一致性上往往**优于**人工代码，因此**更容易通过"扫一眼"的评审**。AI 的特征性缺陷是：

| 失败模式 | 表现 | 判别方法 |
|---------|------|---------|
| **M1 幻觉字段** | 引用不存在的字段/键名，代码自洽但与真实 schema 不通 | 拿 PR 里出现的每一个字段名，去 schema 或前端源码 grep 一次 |
| **M2 乐观路径完备、失败路径缺失** | 主流程写得很漂亮，错误分支是 `catch { console.error(...) }` 就结束了 | 逐个数 catch 分支：如果 catch 里没有"改变用户可感知的状态"，就是缺陷 |
| **M3 静默兜底** | 用 mock、默认值、空数组、`|| 0` 吞掉失败，让流程"跑通" | 搜索本 PR 新增的 `||`、`??`、默认值——每一个都要能回答"这条数据凭什么可以没有" |
| **M4 复制粘贴扩散** | 在同一会话里把某段逻辑复制到 N 个文件，其中只有 1 个被后续修复 | 新代码出现"和某处很像"时，必须在 PR 里列出所有同类位置并说明是否同步 |
| **M5 口径二次实现** | 在业务代码里重新推导一遍已有工具的口径（营收、成本、日期区间） | 改动涉及计算时，先问"这个口径的唯一来源在哪"，答不出来就是新口径 |
| **M6 一次生成巨型文件** | 单次产出 500+ 行组件/函数，混合了 UI、状态、请求、格式化 | 单文件 > 500 行、单函数 > 80 行即触发讨论；> 800 行的 .vue 视为已有拆分红利未兑现 |

### 4.2 AI 代码"三问法"（每个 AI 产出的 PR 必答）

评审者在读完 PR 后，必须能对以下三问给出答案；作者应在 PR 描述中**预先回答**：

1. **问字段**：这次新增/改动的每一个请求体字段名、数据库列名、前端键名，分别在哪些文件里出现过？（蛇形/驼峰机械转换不会自动对齐错名，历史上订单接口已有三例静默取空：`deliveryType`/`deliveryMethod`、`workerId`/`deliveryStaffId`、`createdBy`/`createdById`）
2. **问失败**：这次改动的每条失败路径，用户看到什么？数据库处于什么状态？回滚了吗？
3. **问口径**：这次涉及的任何计算（金额、数量、统计），唯一口径来源是哪个文件？如果没有，为什么这次要新建一个？

### 4.3 AI 生成代码的强制附加要求

- 🔴 **禁止"凭记忆写 SQL / 字段"**。新增或修改 SQL 前必须先确认真实 schema（`database/full_schema_data.sql`）；涉及新字段前必须先 grep 消费侧源码。
- 🔴 **必须提供验证证据**（见第六章 DoD）。AI 说"已修复"不构成证据，冒烟脚本输出、SQL 前后对比、真实浏览器截图才构成。
- 🟡 **改动涉及跨文件复制时，必须在 PR 中列出全部同类位置**，标注"已同步/本次不处理 + 原因"。
- 🟡 **不允许 AI 一次性重构"顺手优化"的无关代码**。混在同一 PR 里的无关改动会掩盖真实缺陷，必须拆开。
- 🟡 **与历史缺陷同类的新代码，必须引用历史缺陷编号**（如"本 PR 遵循 F6 处置方式"），让评审者能快速对齐判断。

### 4.4 评审者心态要求

对 AI 产出，评审者的默认假设应当是：**"这段代码在正常输入下能跑，所以我更需要看它在异常输入下会怎样。"** 正常路径的验证交给测试和冒烟；人的注意力应集中在**边界（0 / null / 负数 / 超大值 / 并发）、失败路径、字段真实存在性、口径唯一性**四处。

## 五、分层检查清单

清单是**最低要求**，不是充分条件。打勾不代表没缺陷。

### 5.1 后端 Controller

- [ ] `req.body` 一律**驼峰单读**，无蛇形别名回退
- [ ] 金额计算走 `Math.round(n * 100) / 100`，无直接浮点比较
- [ ] 分页走 `utils/pagination.js` 的 `parsePage()`，`LIMIT/OFFSET` 为 `parseInt` 内联（mysql2 不支持 `LIMIT ?`）
- [ ] 响应走 `utils/response.js` 的 `success / error / pagination`，无裸 `res.json`
- [ ] 业务校验失败走 **bizFail 模式**（`e.business = true`，controller 统一捕获返回 400 + 回滚），无手写 `rollback()` + `return`
- [ ] 路由具体路径注册在通配 `/:param` **之前**（否则被吞）
- [ ] 新增管理类接口已挂 `requireAdmin`

### 5.2 SQL 与事务

- [ ] 参数化查询；动态表名/字段名**必须**来自服务端白名单（参考 `MODULE_CONFIG`），禁止来自请求
- [ ] 显式列出字段，无 `SELECT *`
- [ ] 涉及"读—判断—写"的并发路径有 `FOR UPDATE` 行锁（余额、库存、欠款）
- [ ] 事务包裹完整：`beginTransaction` 在**所有**校验之前，`commit`/`rollback` 成对，异常路径不漏 rollback
- [ ] 无循环内逐行 `execute`（N+1）；批量操作用多值 INSERT / `CASE WHEN` 批量 UPDATE
- [ ] `IN (...)` 的占位符数量有上限保护（MySQL 上限 65535）
- [ ] 新增查询条件列已确认有可用索引；复合条件考虑联合索引顺序（本项目高频条件：`canceled_at IS NULL` + `order_type` + `created_at` 区间）

### 5.3 数据库迁移

- [ ] 迁移脚本**幂等**（可重复执行），命名 `database/migration_*.sql`
- [ ] 提供对应 `rollback_*.sql`
- [ ] 执行前已 `mysqldump` 备份
- [ ] 执行后重导 `full_schema_data.sql`（`node backend/scripts/export_dump.js`）
- [ ] ⚠️ 已确认导入目标库时使用 `--one-database` 或剥掉 dump 中的 `CREATE DATABASE / USE`（历史事故：直接 `mysql < dump` 打穿正式库）

### 5.4 前端 Vue 组件

- [ ] **失败分支不得误报成功**：`catch` 中不得出现 `ElMessage.success` / 关闭对话框 / 清空表单
- [ ] 无 mock 假数据兜底
- [ ] 对话框窄屏适配：宽度响应式（≤768px 退化为 `94vw`），长表单 `el-dialog__body` 限高滚动，标签窄屏转顶部
- [ ] 菜单/标题只改 `layout/menuConfig.js`，不硬编码
- [ ] `onUnmounted` 中清理：`ResizeObserver`（未 disconnect）、`echarts` 实例（须 `dispose()`）、定时器
- [ ] `<script setup>` 中引用的标识符均已声明（`defineProps` 需先赋 `const props`；机器检查：`npm run check-refs`）
- [ ] `<style>` 中无硬编码色值（机器检查：`node scripts/check_frontend_tokens.js`）
- [ ] 无未使用的 import / 变量
- [ ] 列表页使用 `composables/usePagination.js`，不重写分页样板
- [ ] 金额格式化走 `utils/format.js` 的 `formatMoney`
- [ ] 新增请求走 `src/api/*.js`，禁止组件内裸 `axios`

### 5.5 前端数据与请求

- [ ] **无人为取数上限魔数**：下拉/选项类数据走专用轻量接口或远程搜索；分页数据必须有"超上限"的显式提示
- [ ] 长耗时接口（导入/导出/批量）单独放宽 `timeout`，不得沿用默认值
- [ ] 大文件导入/导出有进度反馈与超时处理，且能区分"前端超时"与"服务端失败"
- [ ] `watch` 中发请求的场景已处理竞态（旧响应不得覆盖新响应）
- [ ] 连续触发型操作（搜索、滚动加载）有防抖/节流
- [ ] > 500 行的表格评估虚拟滚动或服务端分页

### 5.6 脚本与冒烟

- [ ] 写库的 `smoke_*.js` 在 `finally` 调用 `cleanupSmokeResidue(pool)`
- [ ] 测试数据带「冒烟 / smoke_ / SMK / 未来月份」标记
- [ ] 禁止把真实数据（如 `products LIMIT 1`）当测试对象
- [ ] 冒烟脚本数量**只增不减**；修改已有逻辑必须同步更新对应冒烟断言
- [ ] 改后端后**重启服务**再跑冒烟
- [ ] 注意 `loginLimiter`（10 次/15 分钟/IP）：整套冒烟需分批跑或提前重启

## 六、性能与缺陷专项检查

### 6.1 四类必查信号

| 信号 | 检查方法 | 本项目的已知高发处 |
|------|---------|------------------|
| **循环内 I/O** | 看 `for` / `map` 内是否有 `await ... execute/query` | Excel 导入（逐行 execute） |
| **无界取数** | 搜索 PR 新增的 `pageSize:` 字面量、`LIMIT` 字面量 | 20 处硬编码上限，值域 {10,100,200,500,999} |
| **连接池压力** | 长事务 + 高并发路径是否共用 10 连接池；事务是否尽早释放 | `connectionLimit: 10` + `queueLimit: 0`（无界排队） |
| **前端重渲染** | 大表 + 图表同页；`infinite` 动画常驻；watch 连锁请求 | `ProductSales.vue`（表格 + ECharts 同页，取数上限 999） |

### 6.2 后端性能基线要求

- 新增/修改的聚合查询必须能用 `EXPLAIN` 说明走索引，PR 中附 `EXPLAIN` 结果
- 报表类接口的数据聚合在 **SQL 层**完成，禁止"查全量到 Node 再算"
- 新增接口必须评估：单次请求的最坏连接占用时长

### 6.3 前端性能基线要求

- 首屏与路由切换不得引入新的同步大依赖（新增大库需说明按需引入方式，参考 `utils/echarts.js`）
- 表格行数 > 500 或列数 > 20 时，评估虚拟滚动
- 新增常驻动画需说明必要性（历史 A7：5 处 `infinite` 动画已改 hover 触发）
